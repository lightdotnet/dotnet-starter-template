# Coding Conventions: admin

## Build & Tooling

- **Next.js**: 16.3.0, App Router (`src/app/`, no `pages/` directory) — verified in `package.json` and directory listing.
- **Bundler for `next dev`**: `unknown` — `package.json`'s `"dev": "next dev"` has no explicit `--turbopack` flag and `next.config.ts` sets no bundler option.
- **Package manager**: pnpm — `pnpm-lock.yaml` present, no `package-lock.json`/`yarn.lock`. `pnpm-workspace.yaml` configures pnpm's build-script approval (`allowBuilds`/`ignoredBuiltDependencies` for `sharp`, `unrs-resolver`), not a multi-package workspace.
- **`tsconfig.json` strictness**: `"strict": true`, target `ES2017`, module resolution `"bundler"`, path alias `"@/*"` → `"./src/*"`. `components.json`'s finer-grained aliases match this `src/`-rooted layout: `utils` → `@/lib/shared/utils`, `css` → `"src/app/globals.css"`, plus `components`/`ui`/`lib`/`hooks` aliases (`@/components`, `@/components/ui`, `@/lib`, `@/hooks`) resolving under `src/` via the `tsconfig.json` mapping.
- **Styling toolchain**: Tailwind CSS v4 via `@tailwindcss/postcss`, CSS-first config (`src/app/globals.css`).
- **Deploy scripts**: `clients/deploy-nssm.ps1` / `clients/deploy-pm2.ps1` / `clients/init-nssm.ps1` (PowerShell) deploy this app's `output: "standalone"` build to a Windows host — see [development-guide.md](./development-guide.md). Both deploy scripts hoist `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` from the preserved deployed `.env` into the build environment so Server Action IDs stay stable across deploys; that variable is not read by any app runtime code.

## Style

- **Linting**: ESLint 9 flat config (`eslint.config.mjs`), `eslint-config-next`'s `core-web-vitals` + `typescript` rule sets. A scoped override disables `react-hooks/refs` (the React Compiler ESLint rule) for `src/components/{foundation,select,command}/**` — a known false-positive category, since `@floating-ui/react`'s `context`/`refs` objects are read throughout render by design, not the `.current`-during-render hazard the rule targets. The `select` glob segment matches nothing (`components/select/*` doesn't exist) — a harmless no-op flagged in [architecture.md](../architecture/architecture.md#known-architectural-risks--debt). `components/ui/{popover,command,combobox}.tsx` are not covered by this override and haven't needed it.
- **Formatting**: `prettier` + `prettier-plugin-tailwindcss` are devDependencies; no `.prettierrc*` config file and no `format` script exist — `unknown` whether formatting is enforced anywhere.
- **Component file naming**: kebab-case filenames, one primary export per file matching a PascalCase component/function name. `features/*/api/*.ts` uses one consolidated `<feature>.api.ts` file per feature (e.g. `users.api.ts` exports `getAllUsers`, `getDomainUser`, `getUserById`, `searchUsers`, `createUser`, `updateUser`, `forcePassword`, `deleteUser`) rather than one file per endpoint — still kebab-case, still one file per feature. `*-action.ts` Server Action files remain one file per action, kebab-case, named after the action (see the `"use server"` bullet below for the exported names/shapes).
- **`"use client"` directive**: applied to files using hooks/state/browser APIs — `hooks/*`, `components/theme/*`, `components/layout/*` except `brand.tsx` and `deployment-recovery-notice.tsx` (the latter has an inline `onClick` calling `window.location.reload()` but carries no directive of its own — it's only ever imported by the two `"use client"` `error.tsx` boundaries, so it lands in the client bundle transitively), `components/shared/search-box.tsx`, `features/auth/components/login-form.tsx`, `components/shared/data-table/{data-table,data-table-toolbar,data-table-buttons,data-table-pagination,data-table-virtual-body}.tsx`, `components/toast/toaster.tsx` (needs `next-themes`'s `useTheme()`), `features/users/components/{users-data-table,create-user-dialog,edit-user-dialog,delete-user-dialog}.tsx`, `features/roles/components/{roles-data-table,create-role-dialog,edit-role-dialog,delete-role-dialog}.tsx`, `features/notifications/hooks/use-notifications.ts`, `features/notifications/components/{notification-bell,notification-inbox,notifications-data-table,send-notification-dialog,user-select}.tsx`, every file in `components/foundation/*` and `components/command/*`, and `components/ui/native-select.tsx`, `components/ui/{popover,command,combobox}.tsx`, and `components/foundation/portal-container.ts`. One `lib/shared/*` module also carries it: `lib/shared/deployment-recovery.ts` (`"use client"`) — it touches `window`/`sessionStorage`/`fetch` and is imported only by the client error boundaries; the rest of `lib/shared/*` stays directive-free and dual-safe. `components/ui/button-group.tsx` has no hooks and omits the directive, consistent with the "Server Components without hooks" carve-out below. Server Components without hooks (`components/layout/brand.tsx`, `features/auth/components/login-page.tsx`, `features/user-profile/components/user-profile-page.tsx`, `features/users/components/users-page.tsx`, `features/roles/components/roles-page.tsx`, `features/notifications/components/notifications-page.tsx`, `features/home/components/{home-page,profile-summary-card}.tsx`, `components/shared/access-denied.tsx`, `components/ui/button-group.tsx`, all `app/**/page.tsx` and `app/**/layout.tsx`, all `features/*/api/*.ts` files, and `lib/server/require-permission.tsx`) omit it and run server-side — the async data-fetching components (`user-profile-page.tsx`, `login-page.tsx`, `(dashboard)/layout.tsx`, `users-page.tsx`, `roles-page.tsx`, `notifications-page.tsx`, `home-page.tsx`) are `async function`/Server Components, not client-fetched. `src/app/api/health/route.ts` is a Route Handler (`GET` → `204`), not a component — no directive.
- **`"use server"` directive**: 19 modules across seven shapes. 9 use the mutation shape `(prevState, formData) => Promise<{error?: string; success?: boolean}>`, consumed via `useActionState`: `features/auth/api/login-action.ts`, `features/users/api/{create,update,force-password,delete}-user-action.ts`, `features/roles/api/{create,update,delete}-role-action.ts`, `features/notifications/api/send-notification-action.ts`. 2 use the id-arg on-demand-read shape — a plain `(id: string) => Promise<{data, error?}>` called directly (not bound to a `<form>`): `features/users/api/get-user-detail-action.ts`, `features/roles/api/get-role-detail-action.ts`. `features/auth/api/logout-action.ts` (`(redirectTo?: string) => Promise<void>`) is the outlier that returns nothing — it deletes the session cookie and calls `redirect()` itself. Four more shapes from `features/notifications/api/`: a **no-arg read** shape, `get-my-notifications-action.ts` (`() => Promise<{data, error?}>`); a **fire-and-forget-safe** shape, `get-unread-count-action.ts` (`() => Promise<number>`, swallowing any failure to `0` rather than surfacing an error); an **id-arg boolean** shape, `mark-notification-read-action.ts` (`(id) => Promise<boolean>`); and a **token-handoff** shape, `get-signalr-token-action.ts` (`() => Promise<{accessToken} | null>`), which exists specifically to let a Client Component obtain the access token for the SignalR handshake. Three more modules fit the existing **no-arg read** shape or extend it: `features/roles/api/get-all-roles-action.ts` and `features/roles/api/get-permissions-action.ts` (`() => Promise<{data, error?}>`, same bucket as `get-my-notifications-action.ts`) — they exist so `edit-user-dialog.tsx`/`edit-role-dialog.tsx` can self-fetch their picklist on open. `features/users/api/search-users-action.ts` takes a params object rather than an id or no args — `(params: SearchUsersParams) => Promise<{data: Paged<UserDto> | null, error?}>` — a **params-object read** shape, distinct from the existing id-arg/no-arg read shapes; used by `features/notifications/components/user-select.tsx`'s on-demand search. `features/users/api/get-domain-user-action.ts` fits the id-arg on-demand-read shape (`(userName: string) => Promise<{data, error?}>`), backing `create-user-dialog.tsx`'s domain-user lookup. Every mutation `*-action.ts` file calls its underlying `<feature>.api.ts` function through `lib/server/backend-api.ts`, which injects auth itself, so no action extracts/passes `session.accessToken` directly — but each still calls `resolveSession()` and returns the same friendly "Your session has expired..." error when it's `null`.
- **shadcn-generated primitives** (`components/ui/*`, 28 files): `data-slot="<name>"` + `React.ComponentProps<...>` + `cva()` convention, with two exceptions. `popover.tsx`/`command.tsx` follow the convention despite being hand-written rather than CLI-generated (same reasoning as `native-select.tsx`); `combobox.tsx` is a plain composition of the three and doesn't itself wrap a Radix/`cmdk` primitive, so it has no `data-slot`. `button-group.tsx` uses `data-slot="button-group"`/`React.ComponentProps<"div">` but has **no `cva()`** — it's structural (border/rounding utilities toggled by `orientation`), not a variant-driven primitive; provenance (CLI vs hand-written) is `unknown`.
- **UI kit visual conventions**: focus/invalid rings use `ring-2` across `button.tsx`, `input.tsx`, `textarea.tsx`, `checkbox.tsx`, `switch.tsx`, `radio-group.tsx`, plus the hand-rolled search UI — `components/shared/search-box.tsx` (now a `<button>` trigger opening the command palette, not an `<input>`, but still carrying the `focus-visible:ring-2 focus-visible:ring-ring/50` treatment) and `components/shared/data-table/data-table-toolbar.tsx`'s search `<input>`; text-entry-style inputs use `rounded-md` (containers/buttons/popovers use `rounded-lg`); Radix list-style rows the user clicks (`dropdown-menu.tsx`'s item variants, `sidebar-nav-item.tsx`'s expandable-group button) use `cursor-pointer`. The current single-select, `components/ui/combobox.tsx`, is a composition of `popover.tsx` (Radix) and `command.tsx` (`cmdk`) and so inherits the shared `ring-2`/`rounded-lg` popover tokens directly, rather than reproducing them by hand; `native-select.tsx` remains the one hand-rolled exception (no Radix/`cmdk` underneath a real `<select>`), following the same tokens (`ring-2`, `rounded-md`) by hand.

## Structural Conventions

- **Feature folder convention**: `features/<name>/` colocates `api/` (one consolidated `<feature>.api.ts` file per feature, wrapping every backend call that feature makes via `lib/server/backend-api.ts`/`lib/server/http.ts` + `lib/server/call-guard.ts`; `*-action.ts` Server Action files remain one file per action), `components/`, optionally `types/` (either single-consumer, e.g. `features/roles/types/{role,permission-definition}.ts`, or a feature-owned DTO with multiple consumers inside and outside the feature, re-exported via the barrel — e.g. `features/users/types/user.ts`/`features/auth/types/token.ts`; `ClaimDto` lives in a global `types/claim.ts` since `auth`/`users`/`roles` all depend on it equally; `features/notifications/types/notification.ts` is also home to `SendNotificationRequest`), optionally `hooks/` (`features/notifications/hooks/use-notifications.ts` is the one feature-owned hook), optionally `constants/` (permission strings, and one `nav-item.ts` per nav-bearing feature, see below), and a mandatory `index.ts` barrel that re-exports the feature's public surface. **Cross-feature imports must go through the barrel** — verified in the places it's exercised: `features/auth/api/login-action.ts` and `features/users/{components/users-page.tsx,api/create-user-action.ts}` all import from `@/features/user-profile`'s barrel, not `@/features/user-profile/api/user-profile.api` directly. **Seven narrow, deliberate exceptions exist** (see [dependency-graph.md](../architecture/dependency-graph.md#circular-references) and [architecture.md](../architecture/architecture.md#key-design-patterns) for the full list and reasoning): `constants/nav-items.ts` imports each feature's `nav-item.ts` by direct file path; `components/layout/user-menu.tsx` imports `logoutAction` directly; `components/layout/topbar.tsx` imports `NotificationBell` directly; `components/layout/session-gate.tsx` imports `ensureFreshSessionAction` directly; `features/users/components/edit-user-dialog.tsx` imports `getAllRolesAction` directly; `features/notifications/components/user-select.tsx` imports `searchUsersAction` directly; and `features/home/components/home-page.tsx` imports `notification-inbox.tsx` and `get-my-notifications-action.ts` directly. All exist because the target feature's barrel also re-exports server-only code (an async Server Component reading cookies, or a Server Action the barrel doesn't export), and importing the full barrel from client-side code would drag that chain into the client bundle — a reasoned exception, not a violation, scoped narrowly to plain-data/single-component/single-function imports. Two further, lower-level reversals exist at the `lib/server` tier (`refresh-session.ts` → `token.api.ts`, `refetch-profile.ts` → `user-profile.api.ts`).
- **Permission-string constants live per-feature, not in a shared file**: `features/users/constants/permissions.ts` (`USERS_PERMISSIONS`), `features/roles/constants/permissions.ts` (`ROLES_PERMISSIONS`), and `features/notifications/constants/permissions.ts` (`NOTIFICATIONS_PERMISSIONS` — `notification.read`/`notification.send`) each export plain string-literal constants kept in sync by hand with the backend's own permission-string constants, values lowercase and dotted (e.g. `identity.users.view`, `notification.send`) to match what the backend actually issues. **Nav metadata follows the same per-feature-ownership convention**: `features/{home,users,roles,notifications}/constants/nav-item.ts` each own their own `NavItem` (referencing the feature's own permission constant where relevant), and the top-level `constants/nav-items.ts` is purely an assembly file — it composes those into `NAV_ITEMS`, only declaring the "Administration" group and "Settings" leaf directly since neither is owned by a single feature. Both consumers of the assembled tree filter it the same way: `components/layout/sidebar.tsx` via `lib/shared/menu.ts`'s `buildVisibleMenu(NAV_ITEMS, can)`, and `components/shared/search-box.tsx` via the same call plus `flattenNavLeaves` to turn the survivors into command-palette entries.
- **Shared `requirePermission`/`AccessDenied` pattern for page-level permission gating**: `lib/server/require-permission.tsx`'s `requirePermission(permission)` is the sanctioned way for an async Server Component page to gate on a permission — it resolves the session (redirecting to `/login` if none), checks `permission` via `lib/server/authorization.ts`'s `hasPermission`, and returns `{ session, denied }`; the page then does `if (denied) return denied;` before its own data fetch. `denied`, when present, is a shared `components/shared/access-denied.tsx` (`AccessDenied`) element. `users-page.tsx`, `roles-page.tsx`, and `notifications-page.tsx` all use this pattern and behave identically on a missing view permission. Add a new page's gate via `requirePermission` rather than inlining a per-page session-resolve/permission-check/`Empty` block.
- **`app/` is routing-only**: every `page.tsx`/`layout.tsx` under `src/app/` either re-exports a feature component as `default` or composes shared layout chrome (`AppShell`) plus a feature's session-resolution call — no business logic lives in `app/`. The lone Route Handler, `app/api/health/route.ts`, is a trivial `GET` → `204` liveness probe with `export const dynamic = "force-dynamic"`.
- **API-per-feature-file convention**: each `features/*/api/<feature>.api.ts` file wraps every backend HTTP call for that feature (e.g. `users.api.ts` wraps all 8 `Identity.Api` `UserController` calls this app makes), returning a normalized result via one of `guardCall`/`guardResponseCall`/`guardRawCall` (`lib/server/call-guard.ts`) depending on whether the backend endpoint returns a `Result<T>` envelope, a bare `ApiResponse`, or a raw value/array. One consolidated file exists per feature: `features/auth/api/token.api.ts` (`getToken`, `refreshToken`), `features/users/api/users.api.ts`, `features/roles/api/roles.api.ts`, `features/notifications/api/notifications.api.ts` (admin-facing `notification`-route functions) plus a separate `features/notifications/api/user-notifications.api.ts` (self-service `user_notification`-route functions), and `features/user-profile/api/user-profile.api.ts`. Ordinary files pick `identityApi` or `notificationsApi` — whichever ready instance `lib/server/backend-api.ts` exports for the backend module the endpoint belongs to (`const { requestJson } = identityApi;`, following the request-handler-pipeline bullet below) — rather than a single shared, hardcoded client; they don't take an `accessToken` parameter. The pre-session-cookie exceptions — `token.api.ts` (`getToken`/`refreshToken`) and `user-profile.api.ts`'s `getCurrentUser` — import `requestJson`/`requestVoid` from `lib/server/http.ts` directly, since they run before a session cookie exists (`getCurrentUser` takes an explicit `accessToken` parameter and passes it via `explicitBearerTokenHandler`, plus an explicit `client: ApiClients.Identity`; `user-profile.api.ts` is a hybrid file since its `listSessions`/`revokeSession` exports use the ordinary `identityApi` path). `*-action.ts` Server Action files are one file per action, unaffected by this per-feature file consolidation.
- **Request-handler pipeline for auth injection and per-backend client selection, decoupling `lib/server/http.ts` from sessions**: `RequestOptions.handlers?: HttpRequestHandler[]` — each a `(context: { headers: Record<string, string> }) => Promise<void> | void` — runs in order against a shared `headers` object before `fetch()`; `RequestOptions.client: ApiClientName` selects which named backend's base URL to resolve via `lib/server/api-clients.ts`'s registry and is a required field (no default) — the registry has two entries, `Identity`/`Notifications`; `lib/server/config.ts`'s `getApiBaseUrl(client)` resolves the required env var per-client (`IDENTITY_API_BASE_URL`/`NOTIFICATIONS_API_BASE_URL`) and normalizes the result to always end with `/`. `lib/server/http.ts`'s `buildUrl` does not hardcode an `api/v1/` prefix — the configured base URL owns its own full path prefix, resolved directly against the request `path`. `lib/server/backend-api.ts` exports a `createBackendApiClient(client: ApiClientName)` factory plus two ready instances built from it, `identityApi`/`notificationsApi`; `lib/server/http-handlers/bearer-token-handler.ts` exports `bearerTokenHandler` (reads the ambient session, sets `Authorization` if present) and `explicitBearerTokenHandler(accessToken)` (a factory for the pre-session-cookie exceptions above). A service needing a different auth source or backend should call `lib/server/http.ts` directly, or add another `createBackendApiClient(...)` call in `backend-api.ts` for a new backend module, rather than overriding an existing instance's defaults per call.
- **`lib/server/` vs `lib/shared/` split**: `lib/server/*` is server-only (env access, fetch wrapper, cookie helpers/encryption, JWT decoding, token refresh, the page-level permission gate) and must never be imported from a Client Component; `lib/shared/*` is safe for both server and client and is used by 2+ features or layout chrome (`utils.ts`, `dedupe-claims.ts`, `user-display.ts`, `user-status.ts`, `menu.ts`, `authorization.ts`) — the one `lib/shared/*` file that pins `"use client"` is `deployment-recovery.ts`, which is browser-only by nature (`window`/`sessionStorage`/`fetch`) and imported solely by the `error.tsx` boundaries. Permission-checking follows this split explicitly: `lib/shared/authorization.ts` (plain `permissions: string[]`/`userName` parameters, no `SessionData` dependency, so it's usable from the client-side `Sidebar` and `SearchBox`) holds the actual logic, and `lib/server/authorization.ts` is a thin wrapper deriving `userName` from `session.profile?.userName` internally and preserving a `SessionData`-shaped call for server callers. `hasPermission`/`hasAnyPermission`/`hasAllPermissions` are called as `hasPermission(session, permission)`/`hasAnyPermission(session, permissions)`/`hasAllPermissions(session, permissions)`, no separate `userName` argument; callers are `UsersPage`, `RolesPage`, and `NotificationsPage`, all converged onto the same wrapper. `lib/server/require-permission.tsx` composes `resolveSession()`, `lib/server/authorization.ts`, and the shared `components/shared/access-denied.tsx` — it's the one `lib/server/*` module that returns JSX (a `.tsx` file among otherwise-flat `.ts` siblings). `lib/shared/menu.ts` is client-safe — a pure `buildVisibleMenu()`/`flattenNavLeaves()` with no `lib/server/*` dependency. `lib/server/session-cookie.ts` avoids `next/headers` (unlike `lib/server/session.ts`) so `proxy.ts` can import the cookie-name constant and refresh-timing values (`SESSION_TTL_MS`, `REFRESH_LEAD_MS`) without it; `proxy.ts` does pull in Node's `crypto` transitively (via `lib/server/token-cipher.ts`), so whether it still qualifies as edge-runtime-safe is an open question — see [architecture.md](../architecture/architecture.md#known-architectural-risks--debt).
- **Client component boundary**: state/effects/browser API usage pushed into small dedicated hooks/providers (`hooks/use-sidebar.tsx`, `hooks/use-scrolled.ts`, `components/theme/{accent-color-provider,use-has-mounted}`).
- **Centralized toast/pending feedback via two small hooks, not per-dialog duplication**: `hooks/use-guarded-action.ts`'s `useGuardedAction()` (`[pending, run]`, built on `useTransition`) is the sanctioned pattern for an imperative (non-form) mutate-then-toast flow — used by `delete-user-dialog.tsx`/`delete-role-dialog.tsx`, in place of hand-rolled `useTransition` + manual `notifyError`/`notifySuccess` branching (the confirm-dialog UI itself is intentionally not centralized). `hooks/use-action-success-toast.ts`'s `useActionSuccessToast(state, successMessage, onSuccess?)` is the sanctioned pattern for toasting once a `useActionState`-bound result succeeds — used at 6 call sites across 5 form dialogs, in place of a `useEffect` + `notifySuccess(...)` pattern duplicated per dialog.
- **Presentational-only shared components take no feature dependency**: `components/shared/data-table/` is fully generic/controlled via props — it imports only `components/ui/*` and `lib/shared/utils`, never a `features/*` module. Same for `components/toast/`, which wraps `sonner` behind `notifySuccess`/`notifyError` rather than exposing the library directly, and for `components/shared/object-viewer/` (additive — built only on `components/ui/table`/`components/ui/input`, no page/dialog consumes it yet) and `components/shared/access-denied.tsx` (built only on `components/ui/empty.tsx` and `lucide-react`, no `features/*` dependency; its only consumer is `lib/server/require-permission.tsx`, not feature code directly). `components/shared/search-box.tsx` reaches wider than the rest of `components/shared/*` — it imports `@/components/command`, `@/constants/nav-items`, `@/lib/shared/menu`, and `@/lib/shared/authorization` — but all of those are client-safe plain-data/UI, still no `features/*` edge. `components/foundation/*` and `components/command/*` follow the same rule — they import only `@floating-ui/react`/`@tanstack/react-virtual`/`lucide-react`/each other, never `features/*`. `components/ui/combobox.tsx` follows it too — only `components/ui/*`, `lucide-react`, `lib/shared/utils`.
- **Design-token-driven styling**: semantic Tailwind utilities backed by CSS custom properties in `globals.css`'s `@theme inline` block.
- **Error handling**: no `not-found.tsx` under `app/` (see [architecture.md](../architecture/architecture.md#known-architectural-risks--debt)); a root `app/error.tsx` and a `(dashboard)/error.tsx` (rendered inside `AppShell`, since the parent layout stays mounted above an error boundary) exist as client error boundaries. Both branch on `lib/shared/deployment-recovery.ts`'s `isRecoverableDeploymentError(error)` first: a deploy-induced stale-tab error (rotated Server Action ID / `UnrecognizedActionError`, `ChunkLoadError`, a fetch that hit the server mid-restart, Next error `E394`) renders `components/layout/deployment-recovery-notice.tsx`'s `DeploymentRecoveryNotice` and runs `runDeploymentRecovery()` — a `/api/health` poll on a growing backoff that hard-reloads once the server answers, capped at 5 reloads / 5 min via `sessionStorage`; every other error renders the generic destructive `Alert` + `reset()` "Try again" button as before. Every mutation Server Action (`loginAction` and the `{create,update,delete,...}-*-action.ts` files) surfaces failures via a typed `{error?: string}` state returned to `useActionState`, rather than throwing; the two detail-fetch actions (`get-{user,role}-detail-action.ts`) use the analogous `{data, error?}` shape. `logoutAction` is the outlier — it has no failure path to surface (deletes a cookie, redirects) and returns `void`. `call-guard.ts` normalizes thrown errors (network failure, non-2xx status, non-JSON body) into the same `Result`/`ApiResponse` shape the backend itself returns, so UI code only ever handles one shape. `lib/server/http.ts`'s `send()` also extracts a real message from non-2xx bodies (`extractErrorMessage()` — envelope `message` → `ValidationProblemDetails.errors` → `ProblemDetails.title` → generic fallback) before that error reaches `call-guard.ts`, so the normalized result usually carries a specific, backend-authored message rather than a generic one. `UsersPage`/`RolesPage` both pass a `DataTableErrorState`-shaped `error` prop into `DataTable` instead of short-circuiting to a standalone `Alert` — the table (with safe fallback data) always renders, even on a failed fetch; `DataTable` also prioritizes an in-flight reload (`isLoading`) over a stale `error` from a previous failed load, rather than the stale error masking the new loading state.

## Testing Conventions

- **Test framework(s)**: none installed. No Jest/Vitest/Playwright/Testing Library, no `*.test.*`/`*.spec.*` files, no `test` script.
- **Naming convention / mocking library**: not applicable — no test suite exists yet, notable given real auth/session/API logic plus a full create-user flow are all untested.

## Deviations From Norms Elsewhere in the Repo

- Not fully evaluable — `clients/admin` is still the only client app (no sibling under `clients/` to compare against). No deviation from a documented cross-repo convention has been identified; the root `CLAUDE.md`'s stated client-app defaults (Next.js App Router, TypeScript, React) all hold.
- Worth noting for any future sibling app: the `src/`-rooted layout, the feature-folder + barrel convention (one consolidated `<feature>.api.ts` file per feature rather than one file per endpoint), the shared `requirePermission`/`AccessDenied` page-level permission-gate pattern, the two-named-backend-client model (`identityApi`/`notificationsApi` via `createBackendApiClient`), and the `lib/server`/`lib/shared` split are conventions established here first — treat them as a candidate baseline, not yet a cross-repo norm.
