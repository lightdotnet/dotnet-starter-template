# Client App Overview: admin

## Purpose

Internal admin console for the ModularMonolith starter template. Per `src/app/layout.tsx` metadata: "Admin Dashboard" / "Admin dashboard for the ModularMonolith starter kit." This is the **first and only client app** in this template repo (`clients/web` does not exist — verified via directory listing of `clients/`).

The app covers five functional areas plus its own session/chrome layer:

- **Identity administration** (`/identity/users`, `/identity/roles`): full CRUD for users and roles against `Identity.Api`, including a domain-user (Active Directory) lookup on user creation, a permissions checklist plus a free-form "other claims" editor on role editing, and force-password-reset.
- **Notifications** (`/notifications` plus a topbar bell and a Home-page inbox): a permission-gated admin management page with a "Send" action, a live SignalR-backed unread-count/tab-filtered feed shared between the topbar bell and the Home page's two-pane inbox.
- **Organization administration** (`/organization/companies`, `/organization/departments`, `/organization/employees`): full CRUD for companies against `Organization.Api`; a company-scoped department/team hierarchy (`OrgUnit`, unified via a `Type` discriminator) rendered as a recursive tree with add-sub-department/add-team/edit/move/delete actions plus a standalone "View managers" icon button per node (a read-only, on-demand-fetched dialog listing that org unit's active managers), and a company-scoped Employee Levels panel on the same page; full employee CRUD with a tabbed edit dialog (Details / Departments & Teams / Login) covering basic info, department/team membership assignment (level, primary flag, a `Current`/`Acting` status, and a "manager of this department/team" flag — each surfaced as a badge on the membership row), and creating (Email/Phone pre-filled, but editable, from the employee's own record) or linking an Identity login for the employee.
- **Approvals** (`/approvals`): a generic multi-level approval-request workflow against `Approval.Api` — a "Waiting on your decision" table of the caller's own pending approval steps with an approve/reject dialog (optional comment), and, for callers holding `approval.requests.view_all`, an "All approval requests" admin view (most-recent-50, status/level columns) with a "Create test request" dialog that builds an arbitrary-length, ordered approver chain — one row per level, each resolved via an on-demand user-search combobox. This is presently a test/admin harness for the generic engine (there is no real request type, e.g. Leave, driving it automatically yet), exercising the same multi-level "advance on approve" logic a future request type will trigger server-side.
- **Home** (`/`, `features/home/`): a lightweight landing page — a `ProfileSummaryCard` plus the notifications inbox. It is a real Server Component that resolves the session and fetches the caller's own notifications; it does not render any mock/sample data.
- **Auth/session** (`lib/server/*`, `modules/identity/auth/`, `components/layout/session-gate.tsx`, `proxy.ts`): an encrypted, proactively-refreshed cookie session — see Auth Flow below.
- **Deploy-resilience** (`src/app/error.tsx`, `src/app/(dashboard)/error.tsx`, `lib/shared/deployment-recovery.ts`, `src/app/api/health/route.ts`): both error boundaries recognize deploy-induced stale-tab errors — a rotated Server Action ID, a dropped chunk, a fetch that hit the server mid-restart, Next error `E394` — and, instead of the generic error card, show a "new version available / reconnecting" notice that polls `/api/health` on a growing backoff and hard-reloads once the server answers, capped at 5 reloads per 5 minutes via `sessionStorage`.

Each nav-bearing module/feature (`home`, `users`, `roles`, `notifications`, `companies`, `departments`, `employees`, `approvals`) owns its own `NavItem` metadata via a `constants/nav-item.ts`, assembled into `NAV_ITEMS` by the top-level `constants/nav-items.ts` — `home` and `approvals` are top-level leaves, the rest nest under an "Administration" or "Organization" group node (see Key Routes/Areas below); `Sidebar` computes the visible, permission-filtered menu client-side via `lib/shared/menu.ts` (`buildVisibleMenu`) and `lib/shared/authorization.ts` — see architecture.md for the deliberate barrel-bypass this requires. The topbar `SearchBox` reuses the same `buildVisibleMenu(NAV_ITEMS, can)` result (via `lib/shared/menu.ts`'s `flattenNavLeaves`) to populate a ⌘K/Ctrl+K command palette that jumps between pages.

## Structure

- **Router**: App Router, rooted at `src/app/` — verified via directory listing; no `pages/` directory exists.
- **Package manager**: pnpm — verified via `pnpm-lock.yaml`. `pnpm-workspace.yaml` only configures pnpm's build-script approval (`allowBuilds`/`ignoredBuiltDependencies` for `sharp`, `unrs-resolver`) — it does not define a multi-package workspace; `clients/admin` is a single, independent app.
- **Module layout**: almost every feature lives under `src/modules/<domain>/<feature>/` (`identity/{auth,user-profile,users,roles}`, `notifications` — a single flat module, no further nesting — and `organization/{companies,departments,employees}`), plus the new `approvals/` module at the same top level as `identity`/`notifications`/`organization`. **`home` is the one exception**: it stayed at `src/features/home/` (verified via directory listing of both `src/modules/` and `src/features/` — the latter now contains only `home/`). Each module/feature folder keeps the same internal shape regardless of which top-level root it sits under: `api/`, `components/`, optionally `types/`/`constants/`/`hooks/`, and an `index.ts` barrel — see architecture.md's Layering for the full tree.
- **Data fetching approach**: server-only, hand-written per feature/module. Each one's `api/` folder holds one consolidated `<name>.api.ts` file wrapping every backend call it makes — `modules/identity/auth/api/token.api.ts`, `modules/identity/users/api/users.api.ts`, `modules/identity/roles/api/roles.api.ts`, `modules/notifications/api/notifications.api.ts` (admin-facing `notification` routes) plus a separate `modules/notifications/api/user-notifications.api.ts` (self-service `user_notification` routes), `modules/identity/user-profile/api/user-profile.api.ts` (`getCurrentUser`/`listSessions`/`revokeSession`), `modules/organization/companies/api/companies.api.ts`, `modules/organization/departments/api/{org-units,employee-levels}.api.ts`, `modules/organization/employees/api/employees.api.ts`, and `modules/approvals/api/approvals.api.ts` — each normalized through `lib/server/call-guard.ts`. Server Action files (`*-action.ts`) are one file per action, not consolidated. Nearly all of the consolidated files get `requestJson`/`requestVoid` from `lib/server/backend-api.ts`, which pre-wires the bearer-token handler and a named backend client (see Backend Integration below); the pre-session-cookie exceptions — `modules/identity/auth/api/token.api.ts` (`getToken`, `refreshToken`) and `modules/identity/user-profile/api/user-profile.api.ts`'s `getCurrentUser` — import `requestJson`/`requestVoid` from `lib/server/http.ts` directly, passing an explicit token via `explicitBearerTokenHandler` and `client: ApiClients.Identity` (`user-profile.api.ts` is a hybrid file: `getCurrentUser` uses `lib/server/http.ts` this way, while `listSessions`/`revokeSession` in the same file use the ordinary `lib/server/backend-api.ts` path). Whole-list reads happen in async Server Components (`user-profile-page.tsx`, `(dashboard)/layout.tsx`, `users-page.tsx`, `roles-page.tsx`, `companies-page.tsx`, `departments-page.tsx`, `employees-page.tsx`, `approvals-page.tsx`); writes happen via a Next.js Server Action. `modules/notifications` remains the one exception to "server-only fetching": a persistent WebSocket (`@microsoft/signalr`) opened directly from the browser (`use-notifications.ts`), authenticated with a short-lived, server-issued token. `approvals-page.tsx` fetches both `getMyPendingApprovals`/`searchApprovals` server-side (page size 50, no URL-param pagination) and hands the results straight to two plain client components (`MyApprovalsTable`/`AllApprovalsTable`) that render them through the shared `DataTable` with none of its search/pagination props set — a fourth, simpler `DataTable` consumption shape alongside the three already established (see architecture.md's Key Design Patterns).
- **State management**: local component state + React Context, no global state library. See `architecture.md` for the full per-feature inventory; Companies/Departments/Employees follow the same established shapes — `*-data-table.tsx` components drive search/pagination through URL `searchParams`, dialogs use `useActionState` + a bumped remount `key`, `org-unit-tree.tsx` owns its own expand/collapse + active-dialog state (now including a `"managers"` dialog action alongside create/edit/delete/move), and `edit-employee-dialog.tsx` owns its tab-selection state plus a lazily-populated org-unit-tree/employee-level picklist (fetched only once the "Departments & Teams" tab is first activated, not eagerly on dialog open — see architecture.md's Key Design Patterns). Approvals' two tables (`MyApprovalsTable`/`AllApprovalsTable`) hold only local dialog-open/selected-row state — they receive their full record set as server-fetched props and rely on `router.refresh()` (invoked from each dialog's `useGuardedAction`/`onDecided`/`onCreated` callback) rather than owning any search or pagination state of their own.
- **Styling**: Tailwind CSS v4, CSS-first configuration — `src/app/globals.css` uses `@import "tailwindcss"` plus an inline `@theme inline { ... }` block. No `tailwind.config.ts`/`.js` file. `postcss.config.mjs` wires in `@tailwindcss/postcss`.

## Backend Integration

Real, but partial. `lib/server/http.ts` resolves its base URL per named backend client via `lib/server/config.ts`'s `getApiBaseUrl(client)` — `lib/server/api-clients.ts`'s `ApiClients` registry has four entries, `Identity`, `Notifications`, `Organization`, and `Approval`, each resolving its own required server-only env var (`IDENTITY_API_BASE_URL`/`NOTIFICATIONS_API_BASE_URL`/`ORGANIZATION_API_BASE_URL`/`APPROVAL_API_BASE_URL`, see `.env.example`). The base URL owns its full path prefix (e.g. `api/v1/`) — `http.ts`'s `buildUrl` does not hardcode one itself, it resolves the request `path` directly against the (trailing-slash-normalized) base URL. `lib/server/backend-api.ts` exposes this as a `createBackendApiClient(client)` factory, producing four ready instances, `identityApi`/`notificationsApi`/`organizationApi`/`approvalApi`, used by nearly every module's `api/*.ts` file instead of one hardcoded client — the point of the factory shape is that adding a new backend later is just another `createBackendApiClient(...)` call, no sibling file needed (`Approval` is itself the latest demonstration of this — the fourth module added this way). Authorization is attached via a request-handler pipeline rather than a passed-in token: each instance auto-runs `lib/server/http-handlers/bearer-token-handler.ts`'s `bearerTokenHandler`, which reads the ambient session (`getSession()`) and sets `Authorization: Bearer <accessToken>` if present; the pre-session-cookie call sites (`token.api.ts`'s `getToken`/`refreshToken`, `user-profile.api.ts`'s `getCurrentUser`) instead pass the same file's `explicitBearerTokenHandler(accessToken)` directly to `http.ts`, along with an explicit `client: ApiClients.Identity` — `Identity.Api`, `Notifications.Api`, `Organization.Api`, and `Approval.Api` are four logically separate backend modules, currently co-hosted in one process (`StarterKit.WebApi`, `http://localhost:5000`), but the client models them as independently configurable. Non-2xx responses surface a real message where available: `send()`'s `extractErrorMessage` helper reads the response body and prefers, in order, the app's own `ApiResponse.message`, an ASP.NET `ValidationProblemDetails.errors` map, or a `ProblemDetails.title`, falling back to a generic "request failed with status N" message only if none parse — this is shared-kernel and applies to every module's `api/*.ts` call. Non-2xx responses are thrown as a typed `HttpError` (`lib/server/http.ts`, carries the HTTP `status`), which `lib/server/call-guard.ts`'s `errorResponse()` maps to the backend's own `ResultCode` vocabulary (401 → `"unauthorized"`, 400 → `"bad_request"`, anything else — including a network failure with no response at all — → `"error"`) — this is what lets the auth-refresh flow (see Auth Flow below) tell a *permanent* refresh failure (the token itself is invalid) apart from a *transient* one (network/backend outage). **Every response is envelope-wrapped, never a bare value** (the backend's `ApiControllerBase.Ok<T>()` wraps any returned value in a `Result<T>`/`PagedResult<T>` regardless of the controller's declared return type) — `guardCall`/`guardResponseCall`, not `guardRawCall`, is almost always the right `call-guard.ts` helper.

Endpoints currently wired, by feature/module:
- **`auth`**: `auth/token/get` (`getToken()`, POST), `auth/token/refresh` (`refreshToken()`, POST) — both in `modules/identity/auth/api/token.api.ts`, both calling `client: ApiClients.Identity` explicitly; `refreshToken()` is called from `lib/server/refresh-session.ts`'s `refreshSession()`, invoked by `modules/identity/auth/api/ensure-fresh-session-action.ts`'s `ensureFreshSessionAction()` — a Server Action driven client-side by `components/layout/session-gate.tsx` on hard navigation, not proactively by `src/proxy.ts` anymore (see Auth Flow).
- **`user-profile`**: `user_profile` (`getCurrentUser`, GET), `user_profile/token/list` (`listSessions`, GET) and `user_profile/token/revoke` (`revokeSession`, PUT) — all three in `modules/identity/user-profile/api/user-profile.api.ts`, exported from the module barrel; used by `/user-profile`'s session-management UI.
- **`users`**: `user/search` (GET, `searchUsers`), `user` (GET all, `getAllUsers`; PUT-by-id, `updateUser`; DELETE-by-id, `deleteUser`), plus get-by-id, create, force-password, and `get_domain_user/{userName}` (`getDomainUser`, wrapping the backend's `IActiveDirectoryService.GetByUserNameAsync`) — the `Identity.Api` `UserController` surface this app wraps, all in `modules/identity/users/api/users.api.ts`. `user/search` is also used by `search-users-action.ts`, backing on-demand recipient/user search — now with **three** feature-owned duplicates of the same debounced-search pattern: `modules/notifications/components/user-select.tsx`, `modules/organization/employees/components/user-select.tsx`, and `modules/approvals/components/approver-select.tsx` (see architecture.md's Key Design Patterns for why none of the three were promoted to a shared component).
- **`roles`**: `role` (GET all, `getAllRoles`; POST, `createRole`; PUT, `updateRole`; DELETE-by-id, `deleteRole`), plus get-by-id — the full `Identity.Api` `RoleController` surface, all in `modules/identity/roles/api/roles.api.ts`.
- **`permissions`**: `permissions` (GET, `getPermissions`) — the full catalog of definable permissions (`PermissionDefinition { name, displayName, parent }`), now populated by `IdentityPermissionProvider`, `NotificationPermissionProvider`, `OrganizationPermissionProvider`, and `ApprovalPermissionProvider` combined; backs the Roles edit dialog's permissions checklist.
- **`home`**: none directly — `HomePage` (`features/home/`) itself makes no HTTP call beyond `resolveSession()` (cookie-only, no fetch) and `getMyNotificationsAction()`.
- **`notifications`**: `notification` (GET/POST, admin search/send), `user_notification` (self-scoped GET/mark-read/count) — see `modules/notifications/api/{notifications,user-notifications}.api.ts`. Plus a direct WebSocket connection straight to the backend's `/signalr-hub`.
- **`companies`** (`Organization.Api`, client `organizationApi`): `company` (GET, `searchCompanies` — paged, search + status filter; POST, `createCompany`; PUT-by-id, `updateCompany`; DELETE-by-id, `deleteCompany`), plus get-by-id — the full `CompanyController` surface, in `modules/organization/companies/api/companies.api.ts`.
- **`departments`** (`Organization.Api`): `org_unit/company/{companyId}/tree` (GET, `getOrgUnitTree` — the full department/team hierarchy for a company), `org_unit/{id}` (GET/PUT), `org_unit/{id}/move` (PUT, `moveOrgUnit` — reparent), `org_unit` (POST, `createOrgUnit`), `org_unit/{id}` (DELETE), `org_unit/{id}/employee` (GET, `getOrgUnitEmployees`), `org_unit/{id}/manager` (GET, `getOrgUnitManagers` — active memberships flagged `isManager: true` in that org unit, backing the tree's "View managers" dialog) — in `modules/organization/departments/api/org-units.api.ts`; `employee_level/company/{companyId}` (GET, `getEmployeeLevels`), plus create/update/delete — in `modules/organization/departments/api/employee-levels.api.ts`.
- **`employees`** (`Organization.Api`): `employee/search` (GET, paged, company/org-unit/status/text filters), `employee/{id}` (GET, includes membership history), `employee` (POST), `employee/{id}` (PUT/DELETE), `employee/{id}/org_unit` (POST, `assignEmployeeOrgUnit` — request now also carries `assignmentType` (`Current`/`Acting`) and `isManager`), `employee/{id}/org_unit/{orgUnitId}` (PUT, `updateEmployeeMembership` — same two new fields; DELETE, `removeEmployeeFromOrgUnit`), `employee/{id}/login` (POST, `createEmployeeLogin`; PUT, `linkEmployeeLogin`; DELETE, `unlinkEmployeeLogin`) — the full `EmployeeController` surface, in `modules/organization/employees/api/employees.api.ts`. `EmployeeMembershipDto` itself carries the same two new fields (plus the existing `isPrimary`/`levelId`/`levelName`), surfaced as `Acting`/`Manager` badges on each membership row.
- **`approvals`** (`Approval.Api`, client `approvalApi`): `approval/mine` (GET, `getMyPendingApprovals` — paged, the caller's own pending steps), `approval` (GET, `searchApprovals` — paged, `requestType`/`status`/`searchValue` filters; POST, `createApprovalRequest` — request type, title, requester ids, and an ordered `approverChain: ApproverStepInput[]`), `approval/{id}` (GET, `getApprovalById`), `approval/{id}/decide` (PUT, `decideApproval` — `{approved, comment?}`) — the `ApprovalController` surface this app wires, in `modules/approvals/api/approvals.api.ts`.

Each API function returns a normalized `Result`/`ApiResponse`-shaped envelope via `guardCall`/`guardResponseCall`/`guardRawCall` in `lib/server/call-guard.ts`, matching the backend's own `Result<T>` envelope (`types/api.ts`).

`/identity/users`, `/identity/roles`, `/notifications`, `/organization/{companies,departments,employees}`, and `/approvals` all gate on permissions via the shared `lib/server/require-permission.tsx`'s `requirePermission(permission)`. Permission-string constants live per-feature/module: `modules/identity/users/constants/permissions.ts` (`USERS_PERMISSIONS`), `modules/identity/roles/constants/permissions.ts` (`ROLES_PERMISSIONS`), `modules/notifications/constants/permissions.ts` (`NOTIFICATIONS_PERMISSIONS`), `modules/organization/companies/constants/permissions.ts` (`COMPANIES_PERMISSIONS`), `modules/organization/departments/constants/permissions.ts` (`ORG_UNITS_PERMISSIONS`/`EMPLOYEE_LEVELS_PERMISSIONS`), `modules/organization/employees/constants/permissions.ts` (`EMPLOYEES_PERMISSIONS`, including a separate `ManageLogin` permission gating the edit dialog's Login tab), and `modules/approvals/constants/permissions.ts` (`APPROVALS_PERMISSIONS` — `View`, `ViewAll`). The string values match each backend module's own format (lowercase, dotted, module-prefixed — e.g. `organization.companies.view`, `organization.employees.manage_login`, `approval.requests.view_all`).

## Auth Flow

Cookie-based session, encrypted at rest, with proactive token refresh:

1. `/login` → `LoginForm` (`modules/identity/auth/components/login-form.tsx`) submits to `loginAction`, a `"use server"` Server Action (`modules/identity/auth/api/login-action.ts`). When the page was reached via `/login?redirect=<path>`, `LoginPage`/`LoginForm` carry that path through as a hidden `redirect` form field (see step 4). The `Card` UI itself (header, form, submit button) lives entirely in `LoginForm` (a Client Component), not `LoginPage` (an async Server Component that just resolves `searchParams` and centers `<LoginForm redirect={redirect} />`) — `LoginForm` derives `pending` from `useActionState` and renders a dimmed, centered `Spinner` overlay plus a `<fieldset disabled={pending}>` around the inputs while the action is in flight.
2. `loginAction` calls `getToken()` (POST `auth/token/get`, `modules/identity/auth/api/token.api.ts`). On success it also calls `getCurrentUser()` for display/profile data (a failure here doesn't block login — `profile` defaults to `null`). **Permissions and roles are decoded directly from the access token's JWT** (`lib/server/jwt.ts`'s `extractPermissions`/`extractRoles`, reading the `permission`/`role` claim types) — never from the profile API. `SessionData.claims` is the union of every claim in the JWT (`extractAllClaims`) and the profile API's raw claims, deduped via `dedupeClaims()` (`lib/server/build-session-claims.ts`'s `buildSessionClaims()`).
3. The resulting `SessionData` (access/refresh token, absolute access-token expiry, a hard 7-day absolute `sessionExpiresAt` — `SESSION_TTL_MS`, not extended by refresh — claims, permissions, roles, profile, and a `refreshFailureCount` used by step 6 below) is persisted via `persistSessionCookie()` (`lib/server/persist-session-cookie.ts`), which first reduces it to the minimal `StoredSession` shape (`lib/server/stored-session.ts`'s `toStoredSession()`) — `claims`/`permissions`/`roles` are dropped entirely (fully re-derivable from `accessToken`; only `extraClaims`, the delta `claims` doesn't get from decoding `accessToken` alone, is kept) — then JSON-serializes and **encrypts** that reduced shape (`lib/server/token-cipher.ts`'s `encrypt()`, AES-256-GCM, keyed by `TOKEN_ENCRYPTION_KEY`) before writing it to the `admin_session` cookie (`httpOnly`, `sameSite: "lax"`, `path: "/"`, `maxAge` derived from `sessionExpiresAt`) — or, if the encrypted payload still exceeds `MAX_CHUNK_BYTES`, splitting it across numbered `admin_session.0`, `.1`, … chunk cookies instead (`lib/server/cookie-codec.ts`'s `encodeSessionCookies()`), so a broad-permission account's session can't silently exceed the browser's ~4096-byte per-cookie limit. `TOKEN_ENCRYPTION_KEY` is a hard requirement (`lib/server/config.ts`'s `getTokenEncryptionKey()` throws if unset) and is read on every encrypt/decrypt via `token-cipher.ts`.
4. On success, `loginAction` reads the submitted `redirect` field and redirects there if it's a safe same-site relative path (`startsWith("/")` and not `startsWith("//")` — guards against an open redirect), falling back to `/`.
5. `src/proxy.ts` (the Next.js "proxy" convention file, successor to `middleware.ts`) runs on every non-static/non-API request, but only as a thin auth gate — it reassembles, decrypts, validates, and hydrates the cookie(s) (`lib/server/cookie-codec.ts`'s `decodeSessionCookies()` → `stored-session.ts`'s `hydrateSession()`, via `token-cipher.ts`'s `decrypt()`) and checks the hard 7-day `sessionExpiresAt` cap: a missing/expired/malformed session redirects to `/login?redirect=<path>` and clears every cookie in `ALL_SESSION_COOKIE_NAMES` (the base `admin_session` name plus every possible chunk slot), and visiting `/login` with a still-valid session redirects to `/`. It no longer touches token refresh or profile freshness itself — those moved client-side (next step) so a loading UI can be shown while they run, since middleware blocks the whole navigation with no way to render anything during that wait.
6. `components/layout/session-gate.tsx` (`SessionGate`, a Client Component mounted inside `(dashboard)/layout.tsx`, wrapping `AppShell`) drives session freshness instead. It mounts — and so runs its initial check — only on a true hard navigation, since nested layouts don't remount on in-app soft navigation. On mount it calls `modules/identity/auth/api/ensure-fresh-session-action.ts`'s `ensureFreshSessionAction({ refetchProfile: true })` (a Server Action), showing `components/layout/session-loading-overlay.tsx`'s `SessionLoadingOverlay` (a full-page, blurred, spinner overlay) on top of the already-rendered content while it runs. The action calls the shared `refreshSessionIfNearExpiry(session)` (`lib/server/refresh-session.ts`) — same trigger condition as before (`REFRESH_LEAD_MS`, 5 minutes of expiry), returning a `RefreshOutcome` discriminated union (`{status: "skipped"}` / `{status: "success", session}` / `{status: "failed", permanent: boolean}`) so callers can tell "not due" apart from "attempted and failed." `ensureFreshSessionAction` itself then maps that (plus its own permanent-failure-counting logic) to its own exported `EnsureFreshSessionResult` union — `{status: "fresh"}` / `{status: "updated"}` / `{status: "retry"}` / `{status: "degraded"}` — which is what `SessionGate` actually branches on. A `"retry"` result (transient failure — network/5xx, says nothing about the refresh token's validity) makes `SessionGate` retry up to 2 more times (1s/2s backoff); if every attempt keeps failing transiently, it switches to `components/layout/session-unreachable-overlay.tsx`'s `SessionUnreachableOverlay` ("Can't reach the server. Retrying…") and keeps polling every 5s until the backend answers. A **permanent** failure (401/400 — the refresh token itself is invalid/revoked) increments `SessionData.refreshFailureCount` and returns `"degraded"` (a silent, non-gating outcome — the app keeps rendering normally) until the count reaches `MAX_REFRESH_FAILURES` (3, `lib/server/session-cookie.ts`), at which point the action deletes the cookie and calls `redirect("/login")` itself — a genuinely dead session no longer waits out the full 7-day `sessionExpiresAt` cap. On a `"fresh"`/`"updated"` result, and/or (on the initial check only) a profile refetch via `lib/server/refetch-profile.ts`'s `refetchProfile()` (the same `getCurrentUser()` + `buildSessionClaims()` logic that used to live inline in `proxy.ts`), the action persists the updated cookie (`persistSessionCookie()`) and returns `"updated"`, which `SessionGate` answers with `router.refresh()` to re-render the Server Component tree with the fresh cookie. Once the initial check settles (any outcome), `SessionGate` starts a silent 60-second background interval calling `ensureFreshSessionAction({ refetchProfile: false })` — no overlay, no gating — to keep a long-open, soft-navigation-only session's token from going stale.
7. `logoutAction` (`modules/identity/auth/api/logout-action.ts`, `"use server"`) deletes every session cookie (`ALL_SESSION_COOKIE_NAMES`) and redirects to `/login?redirect=<path>` (same open-redirect guard as login) or plain `/login`. `components/layout/user-menu.tsx`'s "Log out" item calls it with the current path (`usePathname()` + `useSearchParams()`) — session-expiry (via `proxy.ts`/`SessionGate`) and explicit logout both funnel through the same `/login?redirect=<path>` → post-login-redirect pattern.
8. `lib/server/session.ts`'s `getSession()` reads and decrypts the cookie (no fetch). `modules/identity/user-profile/api/resolve-session.ts`'s `resolveSession()` is a thin passthrough to `getSession()` — it makes no live `getCurrentUser()` call itself, since `SessionGate` already keeps the cookie's profile/claims fresh on every hard navigation and after each refresh. Used by the dashboard-group layout, the profile page, and every feature/module page under `(dashboard)`.

Note: `token-cipher.ts` uses Node's built-in `crypto` module (`createCipheriv`/`createDecipheriv`) directly, and `proxy.ts` has no explicit `export const runtime` pin — see [architecture.md](./architecture.md#known-architectural-risks--debt) for the resulting flag around which runtime this is verified to require.
