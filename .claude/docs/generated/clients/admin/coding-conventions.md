## Structural Conventions

- **Feature folder convention**: `features/<name>/` colocates `api/` (one file per backend endpoint, wrapping `lib/server/http.ts` + `lib/server/call-guard.ts`), `components/`, optionally `types/` (only when a type has exactly one consumer, e.g. `features/roles/types/{role,permission-definition}.ts`), optionally `hooks/` (`features/notifications/hooks/use-notifications.ts` — the first feature-owned hook), optionally `constants/` (permission strings, and one `nav-item.ts` per nav-bearing feature, see below), and a mandatory `index.ts` barrel that re-exports the feature's public surface. **Cross-feature imports must go through the barrel** — verified in the places it's exercised: `features/auth/api/login-action.ts` and `features/users/{components/users-page.tsx,api/create-user-action.ts}` all import from `@/features/user-profile`'s barrel, not `@/features/user-profile/api/get-current-user` directly; `features/users/components/users-page.tsx` likewise imports `getAllRoles` from `@/features/roles`'s barrel; `features/notifications/components/notifications-page.tsx` likewise imports `getAllUsers` from `@/features/users`'s barrel. **Three narrow, deliberate exceptions exist**: `constants/nav-items.ts` imports each feature's `nav-item.ts` by direct file path rather than via the barrel; `components/layout/user-menu.tsx` imports `logoutAction` directly from `@/features/auth/api/logout-action` rather than the `@/features/auth` barrel (which doesn't currently export it); and `components/layout/topbar.tsx` imports `NotificationBell` directly from `@/features/notifications/components/notification-bell` rather than the `@/features/notifications` barrel, since that barrel also re-exports `NotificationsPage` (an async Server Component reading cookies via `next/headers`). All three are driven by the same reason: the target feature's barrel also re-exports server-only code, and importing the full barrel from client-side code would drag that chain into the client bundle — a reasoned exception to the convention, not a violation, scoped narrowly to plain-data/single-component imports. See [architecture.md](./architecture.md#key-design-patterns) for the full reasoning.
- **Permission-string constants live per-feature, not in a shared file**: `features/users/constants/permissions.ts` (`USERS_PERMISSIONS`), `features/roles/constants/permissions.ts` (`ROLES_PERMISSIONS`), and `features/notifications/constants/permissions.ts` (`NOTIFICATIONS_PERMISSIONS` — `notification.read`/`notification.send`) each export plain string-literal constants kept in sync by hand with the backend's own permission-string constants, values lowercase and dotted (e.g. `identity.users.view`, `notification.send`) to match what the backend actually issues. **Nav metadata follows the same per-feature-ownership move**: `features/{dashboard,users,roles,notifications}/constants/nav-item.ts` each own their own `NavItem` (referencing the feature's own permission constant where relevant), and the top-level `constants/nav-items.ts` is purely an assembly file — it composes those into `NAV_ITEMS`, only declaring the "Identity" group and "Settings" leaf directly since neither is owned by a single feature.
- **`app/` is routing-only**: every `page.tsx`/`layout.tsx` under `src/app/` either re-exports a feature component as `default` or composes shared layout chrome (`AppShell`) plus a feature's session-resolution call — no business logic lives in `app/`.
- **API-per-endpoint-file convention**: each `features/*/api/*.ts` file wraps exactly one backend HTTP call via `requestJson`/`requestVoid` (`lib/server/http.ts`), returning a normalized result via one of `guardCall`/`guardResponseCall`/`guardRawCall` (`lib/server/call-guard.ts`) depending on whether the backend endpoint returns a `Result<T>` envelope, a bare `ApiResponse`, or a raw value/array.
- **`lib/server/` vs `lib/shared/` split**: `lib/server/*` is server-only (env access, fetch wrapper, cookie helpers/encryption, JWT decoding, token refresh) and must never be imported from a Client Component; `lib/shared/*` is safe for both server and client and is used by 2+ features or layout chrome. This sync moved permission-checking into this split explicitly: `lib/shared/authorization.ts` (new — plain `permissions: string[]`/`userName` parameters, no `SessionData` dependency, so it's usable from the client-side `Sidebar`) holds the actual logic, and `lib/server/authorization.ts` is now a thin wrapper preserving the original `(session, userName, permission)` call signature for existing server callers (`UsersPage`, `RolesPage`). `lib/shared/menu.ts` (new) is the other client-safe addition — a pure `buildVisibleMenu()` with no `lib/server/*` dependency. `lib/server/session-cookie.ts` still avoids `next/headers` (unlike `lib/server/session.ts`) so `proxy.ts` can import the cookie-name constant and refresh-timing values (`SESSION_TTL_MS`, `REFRESH_LEAD_MS`) without it; note that `proxy.ts` does now pull in Node's `crypto` transitively (via `lib/server/token-cipher.ts`), so whether it still qualifies as edge-runtime-safe is an open question — see [architecture.md](./architecture.md#known-architectural-risks--debt).
- **Client component boundary**: state/effects/browser API usage pushed into small dedicated hooks/providers (`hooks/use-sidebar.tsx`, `hooks/use-scrolled.ts`, `components/theme/{accent-color-provider,use-has-mounted}`) — unchanged pattern, some files relocated.
- **Presentational-only shared components take no feature dependency**: `components/shared/data-table/` is fully generic/controlled via props — it imports only `components/ui/*` and `lib/shared/utils`, never a `features/*` module. Same for `components/toast/`, which wraps `sonner` behind `notifySuccess`/`notifyError` rather than exposing the library directly, and for `components/shared/object-viewer/` (additive — built only on `components/ui/table`/`components/ui/input`, no page/dialog consumes it yet). `components/foundation/*` and `components/command/*` follow the same rule — they import only `@floating-ui/react`/`@tanstack/react-virtual`/`lucide-react`/each other, never `features/*`. (`components/select/*`, the third member of this group previously, is deleted this sync.) `components/ui/combobox.tsx` (new this sync) follows it too — only `components/ui/*`, `lucide-react`, `lib/shared/utils`.
- **Design-token-driven styling**: unchanged — semantic Tailwind utilities backed by CSS custom properties in `globals.css`'s `@theme inline` block.
- **Error handling**: still no error boundaries, no `error.tsx`/`not-found.tsx` under `app/`. Every mutation Server Action (`loginAction` and the 7 `{create,update,delete,...}-*-action.ts` files) surfaces failures via a typed `{error?: string}` state returned to `useActionState`, rather than throwing; the two detail-fetch actions (`get-{user,role}-detail-action.ts`) use the analogous `{data, error?}` shape. `logoutAction` is the outlier — it has no failure path to surface (deletes a cookie, redirects) and returns `void`. `call-guard.ts` normalizes thrown errors (network failure, non-2xx status, non-JSON body) into the same `Result`/`ApiResponse` shape the backend itself returns, so UI code only ever handles one shape. `lib/server/http.ts`'s `send()` also extracts a real message from non-2xx bodies (`extractErrorMessage()` — envelope `message` → `ValidationProblemDetails.errors` → `ProblemDetails.title` → generic fallback) before that error reaches `call-guard.ts`, so the normalized result usually carries a specific, backend-authored message rather than a generic one. `UsersPage`/`RolesPage` both pass a `DataTableErrorState`-shaped `error` prop into `DataTable` instead of short-circuiting to a standalone `Alert` — the table (with safe fallback data) always renders, even on a failed fetch; `DataTable` also prioritizes an in-flight reload (`isLoading`) over a stale `error` from a previous failed load, rather than the stale error masking the new loading state.
