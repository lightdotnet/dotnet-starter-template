## Structural Conventions

- **Feature folder convention**: `features/<name>/` colocates `api/` (one file per backend endpoint, wrapping `lib/server/http.ts` + `lib/server/call-guard.ts`), `components/`, optionally `types/` (only when a type has exactly one consumer, e.g. `features/roles/types/{role,permission-definition}.ts`), optionally `constants/` (new this cycle — see below), and a mandatory `index.ts` barrel that re-exports the feature's public surface. **Cross-feature imports must go through the barrel** — verified in the places it's exercised: `features/auth/api/login-action.ts` and `features/users/{components/users-page.tsx,api/create-user-action.ts}` all import from `@/features/user-profile`'s barrel, not `@/features/user-profile/api/get-current-user` directly; `features/users/components/users-page.tsx` likewise imports `getAllRoles` from `@/features/roles`'s barrel. `features/roles` gained real `components/` this cycle (`roles-page.tsx`, `roles-data-table.tsx`, `create-role-dialog.tsx`, `edit-role-dialog.tsx`, `delete-role-dialog.tsx`), its first — no feature is purely API-only anymore.
- **Permission-string constants live per-feature, not in a shared file**: `features/users/constants/permissions.ts` (`USERS_PERMISSIONS`) and `features/roles/constants/permissions.ts` (`ROLES_PERMISSIONS`) each export plain string-literal constants kept in sync by hand with the backend's `IdentityPermissions` class (`src/Identity.Contracts/Authorization/IdentityPermissions.cs`). This replaces a former app-wide `constants/permissions.ts` (`IDENTITY_PERMISSIONS`) this cycle — a deliberate move to keep a feature's own authorization strings colocated with the feature that checks them, rather than a general `constants/` folder that otherwise only holds genuinely cross-cutting things (`nav-items.ts`). The string *values* were also corrected this cycle: they're lowercase and dotted with an `identity` prefix (e.g. `identity.users.view`, `identity.roles.manage`), not the `Users.View`-style strings used before, which never matched what the backend actually issues.
- **`app/` is routing-only**: every `page.tsx`/`layout.tsx` under `src/app/` either re-exports a feature component as `default` or composes shared layout chrome (`AppShell`) plus a feature's session-resolution call — no business logic lives in `app/`.
- **API-per-endpoint-file convention**: each `features/*/api/*.ts` file wraps exactly one backend HTTP call via `requestJson`/`requestVoid` (`lib/server/http.ts`), returning a normalized result via one of `guardCall`/`guardResponseCall`/`guardRawCall` (`lib/server/call-guard.ts`) depending on whether the backend endpoint returns a `Result<T>` envelope, a bare `ApiResponse`, or a raw value/array.
- **`lib/server/` vs `lib/shared/` split**: `lib/server/*` is server-only (env access, fetch wrapper, cookie helpers, permission checks — now including `authorization.ts`) and must never be imported from a Client Component; `lib/shared/*` (`utils.ts`, `dedupe-claims.ts`, `user-display.ts`) is safe for both server and client and is used by 2+ features or layout chrome. `lib/server/session-cookie.ts` is deliberately kept free of `next/headers` (unlike `lib/server/session.ts`) so `proxy.ts`, which runs on the edge runtime, can import just the cookie-name constant.
- **Client component boundary**: state/effects/browser API usage pushed into small dedicated hooks/providers (`hooks/use-sidebar.tsx`, `hooks/use-scrolled.ts`, `components/theme/{accent-color-provider,use-has-mounted}`) — unchanged pattern, some files relocated.
- **Presentational-only shared components take no feature dependency**: `components/shared/data-table/` (new) is fully generic/controlled via props — it imports only `components/ui/*` and `lib/shared/utils`, never a `features/*` module. Same for `components/toast/` (new), which wraps `sonner` behind `notifySuccess`/`notifyError` rather than exposing the library directly.
- **Design-token-driven styling**: unchanged — semantic Tailwind utilities backed by CSS custom properties in `globals.css`'s `@theme inline` block.
- **Error handling**: still no error boundaries, no `error.tsx`/`not-found.tsx` under `app/`. Every mutation Server Action (`loginAction` and the 7 `{create,update,delete,...}-*-action.ts` files) surfaces failures via a typed `{error?: string}` state returned to `useActionState`, rather than throwing; the two detail-fetch actions (`get-{user,role}-detail-action.ts`) use the analogous `{data, error?}` shape. `call-guard.ts` normalizes thrown errors (network failure, non-2xx status, non-JSON body) into the same `Result`/`ApiResponse` shape the backend itself returns, so UI code only ever handles one shape. `lib/server/http.ts`'s `send()` also extracts a real message from non-2xx bodies (`extractErrorMessage()` — envelope `message` → `ValidationProblemDetails.errors` → `ProblemDetails.title` → generic fallback) before that error reaches `call-guard.ts`, so the normalized result usually carries a specific, backend-authored message rather than a generic one. `UsersPage`/`RolesPage` both pass a `DataTableErrorState`-shaped `error` prop into `DataTable` instead of short-circuiting to a standalone `Alert` — the table (with safe fallback data) always renders, even on a failed fetch; `DataTable` itself was fixed this cycle so an in-flight reload (`isLoading`) takes priority over a stale `error` from a previous failed load, rather than the stale error masking the new loading state.
