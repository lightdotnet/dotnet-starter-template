# Client App Overview: admin

## Purpose

Internal admin console for the ModularMonolith starter template. Per `src/app/layout.tsx` metadata: "Admin Dashboard" / "Admin dashboard for the ModularMonolith starter kit." This is the **first and only client app** in this template repo (`clients/web` does not exist — verified via directory listing of `clients/`).

Since the last sync: a **Notifications** feature landed — a topbar bell with live SignalR updates (All/Unread/Archived tab filter) plus a permission-gated `/notifications` admin management page with a "Send" action. Before that: the auth/session layer was substantially hardened — the session cookie is now **AES-256-GCM encrypted** (`lib/server/token-cipher.ts`), replacing the previous plaintext-JSON state, and a full **proactive token-refresh flow** now runs inside `src/proxy.ts` on every request (previously unwired); permissions/roles are decoded directly from the access token's JWT (`lib/server/jwt.ts`) rather than sourced elsewhere. Sign-out went from unimplemented to a real `logoutAction` that redirects back through `/login?redirect=<path>`, symmetric with `proxy.ts`'s own session-expiry redirect (the query param itself was also renamed from `from` to `redirect`) — see Auth Flow below. Each nav-bearing feature (`dashboard`, `users`, `roles`) now owns its own `NavItem` metadata via a `constants/nav-item.ts`, assembled into `NAV_ITEMS` by `constants/nav-items.ts`, with `Sidebar` computing the visible menu client-side via new `lib/shared/menu.ts` (`buildVisibleMenu`) and `lib/shared/authorization.ts` helpers — see architecture.md for the deliberate barrel-bypass this required. The shared `DataTable` gained optional per-column client-side sorting (used by the Roles table's Name/Description columns). A new, purely additive `components/shared/object-viewer/` component was ported in but is not yet wired into any page. Minor layout/styling polish: `AppShell`'s `<main>` now uses `bg-sidebar` plus a centered `max-w-7xl` content wrapper, and the sidebar's right border was dropped. The dashboard page itself **still renders static mock data** — unchanged this sync (verified: `features/dashboard/api/sample-data.ts` and its own comment "this UI shell does not call src/Identity.Api yet").

Since the last sync: the app gained an internal, framework-owned select/overlay component library — `components/foundation/`, `components/select/`, `components/command/` — built directly on `@floating-ui/react` (plus `@tanstack/react-virtual` for virtualization) instead of Radix. `components/ui/select.tsx` (the Radix `Select` wrapper) is gone; its three call sites migrated to the new `EntitySelect`/`SearchSelect`. `features/notifications/components/user-select.tsx` no longer stuffs a search `<Input>` inside a Radix `SelectContent` (a documented workaround from a previous sync) — it's now a thin wrapper over `SearchSelect`, with a real clear (X) button and a 3-character minimum before the option list narrows. The Notifications page's status filter dropped its "all" pseudo-option in favor of the new `components/ui/native-select.tsx` (hand-written, not shadcn-CLI-generated) with a real, always-reselectable placeholder. `components/shared/data-table/data-table.tsx` gained an optional `mode` prop (`"paginated"` default, `"virtualized"`, `"infinite"`, the latter two rendering through a new `data-table-virtual-body.tsx`) and an `onSortChange` prop for server-driven sort — both fully backward-compatible; the three existing tables (Users, Roles, Notifications) are unchanged.

Since the last sync: that Floating-UI-based select library is gone again — `components/select/*` (all four components) and most of `components/foundation/*` (`use-floating-popover.ts`, `options-list.tsx`, `use-async-options.ts`, `types.ts`) were deleted, including `AsyncSelect`/`MultiSelect`, which never had a UI consumer. In their place, `components/ui/` gained a standard shadcn-style **Combobox**: `popover.tsx` (a new Radix `Popover` wrapper), `command.tsx` (built on a new `cmdk` dependency), and `combobox.tsx` (`Combobox<TValue>`, composing the two with `Button`). The two real consumers — `edit-user-dialog.tsx`'s status/authProvider fields and `features/notifications/components/user-select.tsx` — were migrated from `EntitySelect`/`SearchSelect` to `Combobox`; `components/command/*` (Command Palette) is untouched and still has no consumer. Building this surfaced two real bugs, both fixed: (1) a `Popover`/`Combobox` nested inside a `Dialog` couldn't be mouse-wheel-scrolled — Radix `Dialog`'s scroll lock only recognizes content that's an actual DOM descendant of its own content node as "inside," but `Popover` portals to `document.body` by default; `DialogContent` now centers via a flex wrapper instead of a CSS `transform` (a `transform` on an ancestor would have broken the nested Popover's `position: fixed` math) and exposes its own DOM node through a new `components/foundation/portal-container.ts` context, which `PopoverContent` reads to portal into the Dialog instead of `document.body` when nested — automatic for any future Combobox-in-Dialog case, not a one-off patch. (2) A sidebar nav group containing the currently-active route could never be manually collapsed — `sidebar-nav-item.tsx` OR'd the user's toggle state with "does this branch contain the active route," so an active branch stayed forced-open regardless of clicks; `hooks/use-sidebar.tsx` now tracks explicit per-href expand/collapse overrides (a `Map<string, boolean>`, `undefined` meaning "no override yet") instead of a plain expanded-`Set`, so an explicit user collapse now wins even while a child route is active.

Since this sync: `data-table-toolbar.tsx` was restructured from one combined search+buttons row into three stacked sections — an actions row, a search row, and a `Separator` inserted between rendered sections — and gained a `customSearch?: React.ReactNode` prop (a caller-supplied multi-field filter UI) plus `onCustomSearch?: () => void` (renders an explicit "Search" button; custom filters apply on click, unlike the built-in single-field `searchValue`/`onSearchChange` text search, which stays auto-debounced). The toolbar no longer builds the Export/Refresh/Columns button cluster itself — a new `components/shared/data-table/data-table-buttons.tsx` (`DataTableButtons`) does, wrapped in a new `components/ui/button-group.tsx` (`ButtonGroup`, a shadcn-style primitive that visually connects adjacent buttons). `data-table.tsx` now computes this buttons node itself and passes it to the toolbar as a `buttons` prop, or — when `customSearch` is used — renders it inside a `rounded-md border border-border` box that now always wraps the table's content (Table/Empty/Alert/virtualized body), right-aligned above the content instead of inline in the toolbar. `features/notifications/components/notifications-data-table.tsx`'s status + recipient filters moved from a standalone block above `<DataTable>` into this new `customSearch` slot and no longer auto-navigate on every change — they hold local "pending" state, applied via `router.push` only when the "Search" button is clicked. `features/users/components/users-data-table.tsx` and `features/roles/components/roles-data-table.tsx`'s row-actions dropdown trigger changed from a `MoreHorizontal` ghost-variant icon button to a bordered (`variant="outline"`) `Pencil` icon button; the dropdown itself is unchanged (still Edit + Delete).

Since this sync: auth-token injection was decoupled from the API layer. `lib/server/http.ts` no longer accepts an `accessToken` option — every request now runs a `handlers?: HttpRequestHandler[]` pipeline (each handler mutates a shared `headers` object before `fetch()`) against a `client?: ApiClientName` resolved by a new `lib/server/api-clients.ts` registry (`ApiClients.Backend`, room for more entries later). A new `lib/server/backend-api.ts` wraps `http.ts`'s `requestJson`/`requestVoid`, auto-injecting a new `lib/server/http-handlers/bearer-token-handler.ts`'s `bearerTokenHandler` (reads the ambient session via `getSession()`) plus `client: ApiClients.Backend`; nearly every `features/*/api/*.ts` file now imports from `backend-api.ts` instead of `http.ts` directly, and their exported functions no longer take an `accessToken` parameter at all. Three call sites that run before a session cookie exists still call `http.ts` directly with an explicit token via the same file's `explicitBearerTokenHandler(accessToken)` factory: `features/auth/api/login.ts` (via `login-action.ts`), `features/auth/api/refresh-token.ts`, and `features/user-profile/api/get-current-user.ts` (called from both `login-action.ts` and `proxy.ts`'s Edge middleware, which has no `next/headers` session access). Every `*-action.ts` Server Action stopped extracting/passing `session.accessToken` to its api function but kept `resolveSession()` plus the "your session has expired" early-exit for the friendly UX message. Two new client-side hooks also landed: `hooks/use-guarded-action.ts` (`useGuardedAction()`, wraps `useTransition` with toast/pending handling for imperative non-form calls — applied to `delete-user-dialog.tsx`/`delete-role-dialog.tsx`) and `hooks/use-action-success-toast.ts` (`useActionSuccessToast()`, a `useEffect` wrapper that toasts and runs a callback once a `useActionState` result's `.success` turns true — applied at 6 call sites across 5 form dialogs), replacing hand-rolled `useTransition`/`notifySuccess` duplication. Trivial, unrelated: `features/notifications/components/notifications-data-table.tsx`'s title column gained `className: "w-[80%]"`.

Since this sync: notifications' WebSocket connection now goes straight from the browser to the backend instead of through the Next.js server. `SIGNALR_HUB_URL` in `use-notifications.ts` changed from a same-origin relative path (proxied by `next.config.ts`'s now-deleted `rewrites()`) to `process.env.NEXT_PUBLIC_SIGNALR_HUB_URL!` — an absolute backend URL, the first `NEXT_PUBLIC_`-prefixed env var in this app (requires backend CORS for the admin origin, assumed already configured backend-side, not verified this sync). `connectSignalR` is now retryable: a failed `connection.start()` logs a sanitized error (a new `sanitizeSignalRErrorMessage()` strips the raw HTML negotiate-failure body SignalR's own error message embeds) and retries after 30 seconds, cleared on unmount. Separately, the session-refresh path feeding SignalR its token was tightened: `getSignalRTokenAction()` now proactively refreshes a near-expiry session before returning the access token, via a new shared `refreshSessionIfNearExpiry()` (`lib/server/refresh-session.ts`) — this closes a gap where `proxy.ts`'s own proactive-refresh middleware excludes `/api` paths from its matcher, so a session left open on one page (no navigation) could hand SignalR a stale/expired token and get a 401. `proxy.ts` and the manual super-admin `refreshSessionAction` (`features/auth/api/refresh-session-action.ts`, previously undocumented here) were both refactored onto this and a second new shared helper, `persistSessionCookie()` (`lib/server/persist-session-cookie.ts`, a Server-Action-context-only cookie writer using `next/headers`'s `cookies()` — not usable from `proxy.ts`'s middleware/Edge context) — pure dedup, no behavior change for either. Unrelated, cosmetic: the accent color picker gained a seventh preset, `black` — the one preset with no Tailwind shade scale, so it inverts across light/dark (`--color-black`/`--color-white`) instead of stepping to a lighter shade like every other preset; `accent-color-picker.tsx`'s swatch rendering gained a `swatchColor()` helper to special-case it.

Since this sync: Notifications gained a real two-pane inbox UI on the Home page, backed by server-side pagination and filtering rather than a client-side slice of one fetched page. Since this sync: fixed a real bug in the topbar bell, found while building the new inbox. `notification-bell.tsx` used to fetch one unfiltered page and filter All/Unread/Archived client-side over just that batch, while its unread badge came from the separate true-total `getUnreadCountAction()` — so the "Unread"/"Archived" tabs could disagree with the badge whenever matching items existed outside the latest page. Also fixed, unrelated: `features/users/api/create-user-action.ts` was reading the wrong `FormData` keys (`userName`/`password` instead of the form's actual field names, `new-userName`/`new-password`), so creating a user always failed client-side with "Username and password are required." even with valid input — pure bug fix, no contract/behavior change beyond that.

Since this sync: `features/users/components/create-user-dialog.tsx` gained a domain-user (Active Directory) lookup against a new backend endpoint, `GET user/get_domain_user/{userName}` (two new files, `features/users/api/get-domain-user.ts`/`get-domain-user-action.ts`, following the existing one-function-per-endpoint convention). The lookup fires two ways — a small ghost icon button (`SearchIcon`/`Spinner`, `size="icon-xs"`) absolutely positioned inside the Username input's own right edge (no separate button beside it), and automatically on the field's `onBlur` once the trimmed value is at least 3 characters and different from the last one looked up (tracked via a `useRef`, deliberately not a debounced `useEffect` — the lookup does not fire per keystroke). A match autofills First/Last name, Email, Phone, sets a new `authProvider` field to `"AD"`, and shows an inline green "User found on domain." line under the Username field (no toast); no match silently resets those same autofilled fields back to blank (including `authProvider`) and shows nothing — a miss just means this will be a local account, not an error. The new `AUTH_PROVIDER_SELECT_OPTIONS` constant represents Local as an **empty string**, not the literal `"Local"` used before — matching the backend's actual convention (`User.ChangeAuthProvider` treats `""`/`null` as "local," and the `AuthProvider` enum itself only defines `AD`; see `src/Identity.Api/Entities/User.cs`/`src/Identity.Contracts/AuthProvider.cs`). `edit-user-dialog.tsx` was migrated onto this same shared constant (it previously defined its own identical-looking `AUTH_PROVIDER_OPTIONS`/`_SELECT_OPTIONS` locally) — its default state and `isLocalAccount` check changed from `"Local"`/`.toLowerCase() === "local"` to `""`/`authProvider === ""` to match, fixing a latent bug where saving an unchanged "Local" selection would have written the literal string `"Local"` into the backend's `AuthProvider` column instead of `null`.

Since this sync, unrelated: two shared UI-primitive fixes found while building the above. `components/ui/tabs.tsx`'s `TabsTrigger` gained `cursor-pointer` — Tailwind's Preflight resets `<button>` to `cursor: default`, and unlike `components/ui/button.tsx` (which already overrides this), `TabsTrigger` never had, so every `Tabs` usage (`edit-user-dialog.tsx`, `notification-inbox.tsx`, `notification-bell.tsx`) showed the arrow cursor on hover instead of a pointer. `components/ui/dialog.tsx`'s `DialogContent` gained `max-h-[calc(100vh-2rem)] overflow-y-auto` — it previously had no height constraint at all, so a dialog taller than a short viewport (e.g. `EditUserDialog`'s tabs + roles + claims) would overflow off-screen with no way to scroll down to its own footer buttons; this scrolls the whole dialog (header + body + footer together) rather than pinning the footer, a deliberate simpler scope than a sticky-footer redesign.

Since this sync: every `features/<name>/api/` folder was refactored from one file per backend-calling function into one consolidated file per feature, with Server Actions left untouched as separate files. `features/auth/api/login.ts`/`refresh-token.ts` were deleted and merged into `features/auth/api/token.api.ts`, which also renames the exported `login()` function to `getToken()` (`refreshToken()` is unchanged). `features/users/api/`'s 8 per-function files were deleted and merged into `features/users/api/users.api.ts` (`getAllUsers`, `getDomainUser`, `getUserById`, `searchUsers`, `createUser`, `updateUser`, `forcePassword`, `deleteUser`). `features/roles/api/`'s 6 per-function files were deleted and merged into `features/roles/api/roles.api.ts` (`getAllRoles`, `getPermissions`, `getRoleById`, `createRole`, `updateRole`, `deleteRole`). `features/notifications/api/get-notifications.ts`/`send-notification.ts` were merged into `features/notifications/api/notifications.api.ts` (the admin-facing `notification`-route functions, `getNotifications`/`sendNotification`; `SendNotificationRequest` moved out of this file into `features/notifications/types/notification.ts`), while `get-my-notifications.ts`/`get-unread-count.ts`/`mark-notification-read.ts` were merged into a separate new `features/notifications/api/user-notifications.api.ts` (the self-service `user_notification`-route functions, `getMyNotifications`/`getUnreadCount`/`markNotificationRead`). `features/user-profile/api/get-current-user.ts`/`list-sessions.ts`/`revoke-session.ts` were merged into `features/user-profile/api/user-profile.api.ts`; `resolve-session.ts` was deliberately left as its own file (it only reads the local session cookie, never calls the backend). No HTTP method/route/query/body changed for any function, and no new features/routes/UI were added — this was a pure file reorganization plus the one `login`→`getToken` rename and the `SendNotificationRequest` relocation. Every `*-action.ts` Server Action file, every feature `index.ts` barrel, `src/proxy.ts`, and the `users-page.tsx`/`roles-page.tsx`/`notifications-page.tsx` page components had their import paths updated to point at the new consolidated files; `lib/server/refresh-session.ts` now imports `refreshToken` from `token.api.ts`.

Since this sync: page-level permission gating was consolidated into two new shared building blocks, replacing three previously separate implementations. A new `lib/server/require-permission.tsx` (`requirePermission(permission)`) resolves the session (redirecting to `/login` if none, via the same `resolveSession()`/`redirect()` call every page used to inline), checks the given permission via `lib/server/authorization.ts`'s `hasPermission`, and returns `{ session, denied }` — a page now does `if (denied) return denied;` instead of inlining `resolveSession`/`redirect`/permission-check/`AccessDenied` JSX itself. The `denied` value, when present, is a new shared `components/shared/access-denied.tsx` (`AccessDenied`, built on `components/ui/empty.tsx`) — previously `users-page.tsx`/`roles-page.tsx` each rendered their own inline `Empty` block for a missing `*.View` permission. `lib/server/authorization.ts`'s `hasPermission`/`hasAnyPermission`/`hasAllPermissions` signatures changed to match: they no longer take a separate `userName` parameter, deriving it from `session.profile?.userName` internally (`lib/shared/authorization.ts`, the underlying client-safe logic, is unchanged). `notifications-page.tsx`, `roles-page.tsx`, and `users-page.tsx` were all migrated onto `requirePermission`. **Real behavior change**: `notifications-page.tsx` previously `redirect()`-ed elsewhere on a missing `notification.read` permission; it now renders the same inline `AccessDenied` as Users/Roles instead — all three pages now behave identically on a missing view permission.

Since this sync, unrelated: `hooks/use-sidebar.tsx`'s nav-group expand/collapse state (`expandedOverrides`) no longer persists to `localStorage` — the `EXPANDED_KEY` constant and its read-on-mount/write-on-change effects were removed, so a manually collapsed/expanded nav group resets to the auto-expand-active-route default on reload. `hidden`/`HIDDEN_KEY` persistence is untouched. The `SidebarContext.Provider` value and its `toggleSidebar`/`isExpanded`/`toggleExpanded` functions were also wrapped in `useMemo`/`useCallback`, a pure internal optimization with no behavior change.

Since this sync: the Roles edit dialog gained an "Other claims" section, separate from the existing Permissions checklist, so claims outside the known permission catalog are editable instead of being silently dropped/overwritten on save. `edit-role-dialog.tsx` classifies each fetched claim on load — a `permission`-type claim only counts as "known" (and gets a pre-checked checkbox) if its value matches a fetched `PermissionDefinition`; everything else, including every `permission` claim when the permissions fetch fails outright, goes into a new `otherClaims: ClaimDto[]` state instead. The new UI lists `otherClaims` as `type: value` rows with a delete button, plus an "Add custom claim" row (Type/Value inputs) that validates non-empty and rejects exact duplicates — `type: "permission"` is allowed here too, letting a role be given an arbitrary/unrecognized permission claim by hand. The array serializes into a new hidden `otherClaims` form field. `features/roles/api/update-role-action.ts` changed to match: it used to silently re-derive non-permission claims by re-fetching `getRoleById(id)` and filtering `claim.type !== "permission"`, discarding any UI edits (there was no UI for them). It now reads the `otherClaims` field via a new `parseOtherClaims(raw, fallbackClaims)` helper — falling back to the unfiltered `current.data.claims` (still fetched via `getRoleById` first, now purely as a validation/fallback source) if the field is missing or malformed — and merges `[...otherClaims, ...permissionClaims]` through `dedupeClaims()` (`lib/shared/dedupe-claims.ts`) before submitting, collapsing any overlap between a manually-added `permission` claim and a checked checkbox. No backend/contract change — `RoleDto.claims: ClaimDto[]` was already generic.

## Structure

- **Router**: App Router, now rooted at `src/app/` (was `app/` directly under `clients/admin/` before this sync) — verified via directory listing; no `pages/` directory exists.
- **Package manager**: pnpm — verified via `pnpm-lock.yaml`. A `pnpm-workspace.yaml` now exists too, but it only configures pnpm's build-script approval (`allowBuilds`/`ignoredBuiltDependencies` for `sharp`, `unrs-resolver`) — it does not define a multi-package workspace; `clients/admin` is still a single, independent app.

## Backend Integration

Real, but partial. `lib/server/http.ts` resolves its base URL per named backend client via `lib/server/config.ts`'s `getApiBaseUrl(client)` — `lib/server/api-clients.ts`'s `ApiClients` registry now has two entries, `Identity` and `Notifications`, each resolving its own required server-only env var (`IDENTITY_API_BASE_URL`/`NOTIFICATIONS_API_BASE_URL`, see `.env.example`). The base URL now owns its full path prefix (e.g. `api/v1/`) — `http.ts`'s `buildUrl` no longer hardcodes one itself, it resolves the request `path` directly against the (trailing-slash-normalized) base URL. `lib/server/backend-api.ts` exposes this as a `createBackendApiClient(client)` factory, producing two ready instances, `identityApi`/`notificationsApi`, used by nearly every `features/*/api/*.ts` file instead of one hardcoded client — the point of the factory shape is that adding a new backend later is just another `createBackendApiClient(...)` call in that same file, no sibling file needed. Authorization is still attached via a request-handler pipeline rather than a passed-in token: each instance auto-runs `lib/server/http-handlers/bearer-token-handler.ts`'s `bearerTokenHandler`, which reads the ambient session (`getSession()`) and sets `Authorization: Bearer <accessToken>` if present; the pre-session-cookie call sites (`token.api.ts`'s `getToken`/`refreshToken`, `user-profile.api.ts`'s `getCurrentUser`) instead pass the same file's `explicitBearerTokenHandler(accessToken)` directly to `http.ts`, along with an explicit `client: ApiClients.Identity` — Identity.Api and Notifications.Api are two logically separate backend modules, currently co-hosted in one process (`StarterKit.WebApi`, `http://localhost:5000`), but the client now models them as independently configurable. Non-2xx responses now surface a real message where available: `send()`'s `extractErrorMessage` helper reads the response body and prefers, in order, the app's own `ApiResponse.message`, an ASP.NET `ValidationProblemDetails.errors` map, or a `ProblemDetails.title`, falling back to the old generic "request failed with status N" message only if none parse — this is shared-kernel and applies to every `features/*/api/*.ts` call, not just `users`.

## Auth Flow

Cookie-based session, encrypted at rest, with proactive token refresh:

1. `/login` → `LoginForm` (`features/auth/components/login-form.tsx`) submits to `loginAction`, a `"use server"` Server Action (`features/auth/api/login-action.ts`). When the page was reached via `/login?redirect=<path>`, `LoginPage`/`LoginForm` carry that path through as a hidden `redirect` form field (see step 4). **Changed this sync**: the `Card` UI itself (header, form, submit button) now lives entirely in `LoginForm` (a Client Component), not `LoginPage` (the async Server Component) — `LoginForm` derives `pending` from `useActionState` and renders a dimmed, centered `Spinner` overlay plus a `<fieldset disabled={pending}>` around the inputs while the action is in flight; `LoginPage` is now just a thin wrapper that resolves `searchParams` and centers `<LoginForm redirect={redirect} />` on the page.
2. `loginAction` calls `getToken()` (POST `auth/token/get`; renamed from `login()` in a prior sync, now consolidated into `features/auth/api/token.api.ts`). On success it also calls `getCurrentUser()` for display/profile data (a failure here doesn't block login — `profile` defaults to `null`). **Permissions and roles are decoded directly from the access token's JWT** (`lib/server/jwt.ts`'s `extractPermissions`/`extractRoles`, reading the `permission`/`role` claim types) — never from the profile API. `SessionData.claims` is the union of every claim in the JWT (`extractAllClaims`) and the profile API's raw claims, deduped via `dedupeClaims()` (`lib/server/build-session-claims.ts`'s `buildSessionClaims()`).
3. The resulting `SessionData` (access/refresh token, absolute access-token expiry, a hard 7-day absolute `sessionExpiresAt` — `SESSION_TTL_MS`, not extended by refresh — claims, permissions, roles, profile) is JSON-serialized and **encrypted** (`lib/server/token-cipher.ts`'s `encrypt()`, AES-256-GCM, keyed by `TOKEN_ENCRYPTION_KEY`) before being written to the `admin_session` cookie (`httpOnly`, `sameSite: "lax"`, `path: "/"`, `maxAge` derived from `sessionExpiresAt`). The former "plaintext for now" state is gone: `TOKEN_ENCRYPTION_KEY` is a hard requirement now (`lib/server/config.ts`'s `getTokenEncryptionKey()` throws if unset) and is read on every encrypt/decrypt via `token-cipher.ts`.
4. On success, `loginAction` reads the submitted `redirect` field and redirects there if it's a safe same-site relative path (`startsWith("/")` and not `startsWith("//")` — guards against an open redirect), falling back to `/`.
5. `src/proxy.ts` (the Next.js 16 "proxy" convention file, successor to `middleware.ts`) runs on every non-static/non-API request. It decrypts and validates the cookie (`lib/server/parse-session.ts`'s `parseSessionCookie()` → `token-cipher.ts`'s `decrypt()`); a missing/expired/malformed session (past `sessionExpiresAt`) redirects to `/login?redirect=<path>` and clears the cookie, and visiting `/login` with a still-valid session redirects to `/`. It calls the shared `refreshSessionIfNearExpiry(session)` (`lib/server/refresh-session.ts` — extracted out of `proxy.ts`'s own inline `REFRESH_LEAD_MS` check into a reusable helper, also used by `getSignalRTokenAction()`, see Backend Integration), which proactively rotates the token via `refreshSession()` (calling the backend's `auth/token/refresh` via `features/auth/api/token.api.ts`'s `refreshToken` and re-decoding permissions/roles from the newly-issued token) once within `REFRESH_LEAD_MS` (5 minutes) of expiry — a not-due check and a failed refresh both return `null` and neither is treated as a dead session (the code's own comment: multi-tab refresh races can look identical to a real failure, and the backend's own calls still enforce revocation). On a hard navigation (full page load, detected via the `Sec-Fetch-Dest: document` header — Next.js's own client-side route transitions don't send it) or right after a refresh, it also refetches display/claims data via `getCurrentUser()` and rewrites the re-encrypted cookie on both the outgoing request and the response. **This is the token-refresh flow the previous doc version reported as unwired — it is now fully implemented, inside `proxy.ts` rather than a separate scheduled job or client-side call.**
6. `logoutAction` (`features/auth/api/logout-action.ts`, `"use server"`) deletes the session cookie and redirects to `/login?redirect=<path>` (same open-redirect guard as login) or plain `/login`. `components/layout/user-menu.tsx`'s "Log out" item calls it with the current path (`usePathname()` + `useSearchParams()`). **This closes a previously-documented gap** ("Sign-out has no implementation") — session-expiry (via `proxy.ts`) and explicit logout now both funnel through the same `/login?redirect=<path>` → post-login-redirect pattern.
7. `lib/server/session.ts`'s `getSession()` reads and decrypts the cookie (no fetch). `features/user-profile/api/resolve-session.ts`'s `resolveSession()` is now a thin passthrough to `getSession()` — it no longer makes a live `getCurrentUser()` call itself, since `proxy.ts` already keeps the cookie's profile/claims fresh on every hard navigation and after each refresh. Used by the dashboard-group layout, the profile page, and both `UsersPage`/`RolesPage`.

Note: `token-cipher.ts` uses Node's built-in `crypto` module (`createCipheriv`/`createDecipheriv`) directly, and `proxy.ts` has no explicit `export const runtime` pin — see [architecture.md](./architecture.md#known-architectural-risks--debt) for the resulting flag around which runtime this is verified to require.
