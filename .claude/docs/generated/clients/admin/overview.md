# Client App Overview: admin

## Purpose

Internal admin console for the ModularMonolith starter template. Per `src/app/layout.tsx` metadata: "Admin Dashboard" / "Admin dashboard for the ModularMonolith starter kit." This is the **first and only client app** in this template repo (`clients/web` does not exist — verified via directory listing of `clients/`).

Since the last sync: a **Notifications** feature landed — a topbar bell with live SignalR updates (All/Unread/Archived tab filter) plus a permission-gated `/notifications` admin management page with a "Send" action. Before that: the auth/session layer was substantially hardened — the session cookie is now **AES-256-GCM encrypted** (`lib/server/token-cipher.ts`), replacing the previous plaintext-JSON state, and a full **proactive token-refresh flow** now runs inside `src/proxy.ts` on every request (previously unwired); permissions/roles are decoded directly from the access token's JWT (`lib/server/jwt.ts`) rather than sourced elsewhere. Sign-out went from unimplemented to a real `logoutAction` that redirects back through `/login?redirect=<path>`, symmetric with `proxy.ts`'s own session-expiry redirect (the query param itself was also renamed from `from` to `redirect`) — see Auth Flow below. Each nav-bearing feature (`dashboard`, `users`, `roles`) now owns its own `NavItem` metadata via a `constants/nav-item.ts`, assembled into `NAV_ITEMS` by `constants/nav-items.ts`, with `Sidebar` computing the visible menu client-side via new `lib/shared/menu.ts` (`buildVisibleMenu`) and `lib/shared/authorization.ts` helpers — see architecture.md for the deliberate barrel-bypass this required. The shared `DataTable` gained optional per-column client-side sorting (used by the Roles table's Name/Description columns). A new, purely additive `components/shared/object-viewer/` component was ported in but is not yet wired into any page. Minor layout/styling polish: `AppShell`'s `<main>` now uses `bg-sidebar` plus a centered `max-w-7xl` content wrapper, and the sidebar's right border was dropped. The dashboard page itself **still renders static mock data** — unchanged this sync (verified: `features/dashboard/api/sample-data.ts` and its own comment "this UI shell does not call src/Identity.Api yet").

Since the last sync: the app gained an internal, framework-owned select/overlay component library — `components/foundation/`, `components/select/`, `components/command/` — built directly on `@floating-ui/react` (plus `@tanstack/react-virtual` for virtualization) instead of Radix. `components/ui/select.tsx` (the Radix `Select` wrapper) is gone; its three call sites migrated to the new `EntitySelect`/`SearchSelect`. `features/notifications/components/user-select.tsx` no longer stuffs a search `<Input>` inside a Radix `SelectContent` (a documented workaround from a previous sync) — it's now a thin wrapper over `SearchSelect`, with a real clear (X) button and a 3-character minimum before the option list narrows. The Notifications page's status filter dropped its "all" pseudo-option in favor of the new `components/ui/native-select.tsx` (hand-written, not shadcn-CLI-generated) with a real, always-reselectable placeholder. `components/shared/data-table/data-table.tsx` gained an optional `mode` prop (`"paginated"` default, `"virtualized"`, `"infinite"`, the latter two rendering through a new `data-table-virtual-body.tsx`) and an `onSortChange` prop for server-driven sort — both fully backward-compatible; the three existing tables (Users, Roles, Notifications) are unchanged.

Since the last sync: that Floating-UI-based select library is gone again — `components/select/*` (all four components) and most of `components/foundation/*` (`use-floating-popover.ts`, `options-list.tsx`, `use-async-options.ts`, `types.ts`) were deleted, including `AsyncSelect`/`MultiSelect`, which never had a UI consumer. In their place, `components/ui/` gained a standard shadcn-style **Combobox**: `popover.tsx` (a new Radix `Popover` wrapper), `command.tsx` (built on a new `cmdk` dependency), and `combobox.tsx` (`Combobox<TValue>`, composing the two with `Button`). The two real consumers — `edit-user-dialog.tsx`'s status/authProvider fields and `features/notifications/components/user-select.tsx` — were migrated from `EntitySelect`/`SearchSelect` to `Combobox`; `components/command/*` (Command Palette) is untouched and still has no consumer. Building this surfaced two real bugs, both fixed: (1) a `Popover`/`Combobox` nested inside a `Dialog` couldn't be mouse-wheel-scrolled — Radix `Dialog`'s scroll lock only recognizes content that's an actual DOM descendant of its own content node as "inside," but `Popover` portals to `document.body` by default; `DialogContent` now centers via a flex wrapper instead of a CSS `transform` (a `transform` on an ancestor would have broken the nested Popover's `position: fixed` math) and exposes its own DOM node through a new `components/foundation/portal-container.ts` context, which `PopoverContent` reads to portal into the Dialog instead of `document.body` when nested — automatic for any future Combobox-in-Dialog case, not a one-off patch. (2) A sidebar nav group containing the currently-active route could never be manually collapsed — `sidebar-nav-item.tsx` OR'd the user's toggle state with "does this branch contain the active route," so an active branch stayed forced-open regardless of clicks; `hooks/use-sidebar.tsx` now tracks explicit per-href expand/collapse overrides (a `Map<string, boolean>`, `undefined` meaning "no override yet") instead of a plain expanded-`Set`, so an explicit user collapse now wins even while a child route is active.

Since this sync: `data-table-toolbar.tsx` was restructured from one combined search+buttons row into three stacked sections — an actions row, a search row, and a `Separator` inserted between rendered sections — and gained a `customSearch?: React.ReactNode` prop (a caller-supplied multi-field filter UI) plus `onCustomSearch?: () => void` (renders an explicit "Search" button; custom filters apply on click, unlike the built-in single-field `searchValue`/`onSearchChange` text search, which stays auto-debounced). The toolbar no longer builds the Export/Refresh/Columns button cluster itself — a new `components/shared/data-table/data-table-buttons.tsx` (`DataTableButtons`) does, wrapped in a new `components/ui/button-group.tsx` (`ButtonGroup`, a shadcn-style primitive that visually connects adjacent buttons). `data-table.tsx` now computes this buttons node itself and passes it to the toolbar as a `buttons` prop, or — when `customSearch` is used — renders it inside a `rounded-md border border-border` box that now always wraps the table's content (Table/Empty/Alert/virtualized body), right-aligned above the content instead of inline in the toolbar. `features/notifications/components/notifications-data-table.tsx`'s status + recipient filters moved from a standalone block above `<DataTable>` into this new `customSearch` slot and no longer auto-navigate on every change — they hold local "pending" state, applied via `router.push` only when the "Search" button is clicked. `features/users/components/users-data-table.tsx` and `features/roles/components/roles-data-table.tsx`'s row-actions dropdown trigger changed from a `MoreHorizontal` ghost-variant icon button to a bordered (`variant="outline"`) `Pencil` icon button; the dropdown itself is unchanged (still Edit + Delete).

Since this sync: auth-token injection was decoupled from the API layer. `lib/server/http.ts` no longer accepts an `accessToken` option — every request now runs a `handlers?: HttpRequestHandler[]` pipeline (each handler mutates a shared `headers` object before `fetch()`) against a `client?: ApiClientName` resolved by a new `lib/server/api-clients.ts` registry (`ApiClients.Backend`, room for more entries later). A new `lib/server/backend-api.ts` wraps `http.ts`'s `requestJson`/`requestVoid`, auto-injecting a new `lib/server/http-handlers/bearer-token-handler.ts`'s `bearerTokenHandler` (reads the ambient session via `getSession()`) plus `client: ApiClients.Backend`; nearly every `features/*/api/*.ts` file now imports from `backend-api.ts` instead of `http.ts` directly, and their exported functions no longer take an `accessToken` parameter at all. Three call sites that run before a session cookie exists still call `http.ts` directly with an explicit token via the same file's `explicitBearerTokenHandler(accessToken)` factory: `features/auth/api/login.ts` (via `login-action.ts`), `features/auth/api/refresh-token.ts`, and `features/user-profile/api/get-current-user.ts` (called from both `login-action.ts` and `proxy.ts`'s Edge middleware, which has no `next/headers` session access). Every `*-action.ts` Server Action stopped extracting/passing `session.accessToken` to its api function but kept `resolveSession()` plus the "your session has expired" early-exit for the friendly UX message. Two new client-side hooks also landed: `hooks/use-guarded-action.ts` (`useGuardedAction()`, wraps `useTransition` with toast/pending handling for imperative non-form calls — applied to `delete-user-dialog.tsx`/`delete-role-dialog.tsx`) and `hooks/use-action-success-toast.ts` (`useActionSuccessToast()`, a `useEffect` wrapper that toasts and runs a callback once a `useActionState` result's `.success` turns true — applied at 6 call sites across 5 form dialogs), replacing hand-rolled `useTransition`/`notifySuccess` duplication. Trivial, unrelated: `features/notifications/components/notifications-data-table.tsx`'s title column gained `className: "w-[80%]"`.

Since this sync: notifications' WebSocket connection now goes straight from the browser to the backend instead of through the Next.js server. `SIGNALR_HUB_URL` in `use-notifications.ts` changed from a same-origin relative path (proxied by `next.config.ts`'s now-deleted `rewrites()`) to `process.env.NEXT_PUBLIC_SIGNALR_HUB_URL!` — an absolute backend URL, the first `NEXT_PUBLIC_`-prefixed env var in this app (requires backend CORS for the admin origin, assumed already configured backend-side, not verified this sync). `connectSignalR` is now retryable: a failed `connection.start()` logs a sanitized error (a new `sanitizeSignalRErrorMessage()` strips the raw HTML negotiate-failure body SignalR's own error message embeds) and retries after 30 seconds, cleared on unmount. Separately, the session-refresh path feeding SignalR its token was tightened: `getSignalRTokenAction()` now proactively refreshes a near-expiry session before returning the access token, via a new shared `refreshSessionIfNearExpiry()` (`lib/server/refresh-session.ts`) — this closes a gap where `proxy.ts`'s own proactive-refresh middleware excludes `/api` paths from its matcher, so a session left open on one page (no navigation) could hand SignalR a stale/expired token and get a 401. `proxy.ts` and the manual super-admin `refreshSessionAction` (`features/auth/api/refresh-session-action.ts`, previously undocumented here) were both refactored onto this and a second new shared helper, `persistSessionCookie()` (`lib/server/persist-session-cookie.ts`, a Server-Action-context-only cookie writer using `next/headers`'s `cookies()` — not usable from `proxy.ts`'s middleware/Edge context) — pure dedup, no behavior change for either. Unrelated, cosmetic: the accent color picker gained a seventh preset, `black` — the one preset with no Tailwind shade scale, so it inverts across light/dark (`--color-black`/`--color-white`) instead of stepping to a lighter shade like every other preset; `accent-color-picker.tsx`'s swatch rendering gained a `swatchColor()` helper to special-case it.

## Structure

- **Router**: App Router, now rooted at `src/app/` (was `app/` directly under `clients/admin/` before this sync) — verified via directory listing; no `pages/` directory exists.
- **Package manager**: pnpm — verified via `pnpm-lock.yaml`. A `pnpm-workspace.yaml` now exists too, but it only configures pnpm's build-script approval (`allowBuilds`/`ignoredBuiltDependencies` for `sharp`, `unrs-resolver`) — it does not define a multi-package workspace; `clients/admin` is still a single, independent app.
- **Data fetching approach**: server-only, hand-written per endpoint — every `features/<name>/api/*.ts` file wraps one backend call, normalized through `lib/server/call-guard.ts`. Nearly all of them get `requestJson`/`requestVoid` from the new `lib/server/backend-api.ts`, which pre-wires the bearer-token handler and `ApiClients.Backend` (see Backend Integration below); the 3 exceptions that run before a session cookie exists (`features/auth/api/{login,refresh-token}.ts`, `features/user-profile/api/get-current-user.ts`) still import `requestJson`/`requestVoid` from `lib/server/http.ts` directly, passing an explicit token via `explicitBearerTokenHandler`. Whole-list reads happen in async Server Components (`user-profile-page.tsx`, `(dashboard)/layout.tsx`, `features/users/components/users-page.tsx`, `features/roles/components/roles-page.tsx`); writes happen via a Next.js Server Action — 8 of them, all `"use server"`, same `(prevState, formData) => Promise<{error?, success?}>` shape: `features/auth/api/login-action.ts`, `features/users/api/{create,update,force-password,delete}-user-action.ts`, `features/roles/api/{create,update,delete}-role-action.ts`. Five more Server Actions serve a third purpose — an on-demand *read* triggered from a Client Component when a list row's own data isn't complete enough, or when a picklist itself is no longer preloaded by the page (see [architecture.md](./architecture.md) for why): `features/users/api/get-user-detail-action.ts` and `features/roles/api/get-role-detail-action.ts` fetch a single record's full detail on dialog open; new this sync, `features/roles/api/get-all-roles-action.ts` and `features/roles/api/get-permissions-action.ts` (both a plain `() => Promise<{data, error?}>`) let `edit-user-dialog.tsx`/`edit-role-dialog.tsx` fetch their own role/permission picklists on open, now that `users-page.tsx`/`roles-page.tsx` no longer preload them; and `features/users/api/search-users-action.ts` (`(params: SearchUsersParams) => Promise<{data: Paged<UserDto> | null, error?}>`) backs the new on-demand recipient search in `features/notifications/components/user-select.tsx`. No client-side data-fetching library (no React Query/SWR in `package.json`) for HTTP requests — this still holds. `features/notifications` adds a new category of client-side networking, though: a persistent WebSocket (`@microsoft/signalr`) opened directly from the browser (`use-notifications.ts`), not a fetch-based library. `getAllUsers`'s previous eager-preload pattern is gone from Notifications entirely — see below. The dashboard page is the one HTTP exception — it still reads static arrays from `features/dashboard/api/sample-data.ts` instead of calling the backend.
- **State management**: local component state + React Context, no global state library:
  - `hooks/use-sidebar.tsx` (`SidebarProvider`/`useSidebar`) — sidebar hidden/expanded/mobile-open state, persisted to `localStorage`.
  - `components/theme/accent-color-provider.tsx` (`AccentColorProvider`/`useAccentColor`) — accent color selection, persisted to `localStorage`, applied via `data-accent` on `<html>`. Moved here from a former `hooks/use-accent-color.tsx`.
  - `components/theme/theme-provider.tsx` — thin wrapper around `next-themes`' `ThemeProvider`. Moved here from a former top-level `providers/` folder.
  - `features/dashboard/components/users-table.tsx` — local `useState` for pagination (`page`).
  - `features/auth/components/login-form.tsx` — `useActionState` bound to the `loginAction` server action.
  - `features/users/components/users-data-table.tsx` — drives search/pagination through URL `searchParams` via `router.push`/`router.refresh()` wrapped in `useTransition`; owns open/selected-row state for all three dialogs (create/edit/delete) plus a per-dialog remount-key counter used to force-remount each on every open.
  - `features/users/components/{create,edit}-user-dialog.tsx` — `useActionState` bound to their respective Server Actions, plus a parallel controlled `useState<FormValues>` for the form fields (deliberate — see [architecture.md](./architecture.md) for why). `edit-user-dialog.tsx` additionally holds its own `roles: RoleDto[]` state and, on open, runs `Promise.all([getUserDetailAction(user.id), getAllRolesAction()])` in a `useEffect` — fetching both the full user record (the list endpoint's DTO doesn't carry `roles`/`claims`) and the role picklist itself, now that `users-page.tsx` no longer preloads and passes it down.
  - `features/users/components/delete-user-dialog.tsx` (new) — now via `hooks/use-guarded-action.ts`'s `useGuardedAction()` (`[pending, run]`, wraps `useTransition` with toast/pending handling) wrapping a direct (non-form) call to `deleteUserAction`, previously hand-rolled `useTransition`.
  - `features/roles/components/roles-data-table.tsx` (new) — same shape as `users-data-table.tsx`, but drives search via local `useState` + client-side `.filter()` instead of URL params, since `RoleController` has no search/pagination endpoint.
  - `features/roles/components/edit-role-dialog.tsx` (new) — same "fetch full detail on open" pattern as `edit-user-dialog.tsx`, via `getRoleDetailAction`; likewise now holds its own `permissions: PermissionDefinition[]` state and, on open, runs `Promise.all([getRoleDetailAction(role.id), getPermissionsAction()])` since `roles-page.tsx` no longer preloads the permission catalog.
  - `features/notifications/components/user-select.tsx` (rewritten) — no longer a thin wrapper; owns its own `open`/`query`/`options`/`loading`/`selectedLabel` state. A debounced (300ms) `useEffect` calls `searchUsersAction` for page 1 of matches once the trimmed query reaches the minimum search length, replacing the previous preloaded-list + client-side-filter approach.
  - `components/shared/data-table/data-table-toolbar.tsx` — local debounced search-text state (400ms) before calling the `onSearchChange` prop (unchanged for the built-in text search); no longer owns any button-cluster state — Export/Refresh/Columns moved to the new `data-table-buttons.tsx`, driven by `data-table.tsx`'s own `hiddenColumnIds` state. `data-table-pagination.tsx` — local page-jump input state, committed on blur/Enter.
  - `features/notifications/components/notifications-data-table.tsx` (new this sync) — local "pending" status/recipient filter state (`pendingStatus`/`pendingToUserId`), applied to the URL only when the `customSearch` slot's "Search" button is clicked; re-synced from props when the URL changes externally, mirroring `data-table-toolbar.tsx`'s own search-value-sync pattern.
  - `features/notifications/hooks/use-notifications.ts` (new) — owns `notifications`/`unreadCount`/`loading` state; opens a `HubConnection` (`@microsoft/signalr`) in a `useEffect` and refetches on every `SystemMessage` push rather than merging the pushed payload in place.
  - `hooks/use-guarded-action.ts` (new) — `useGuardedAction()` returns `[pending, run]`; `run(action, successMessage?, onSuccess?)` wraps `useTransition`, toasting success/error and invoking `onSuccess`. Used by `features/users/components/delete-user-dialog.tsx` and `features/roles/components/delete-role-dialog.tsx`, replacing each dialog's own hand-rolled `useTransition` + manual `notifyError`/`notifySuccess` branching.
  - `hooks/use-action-success-toast.ts` (new) — `useActionSuccessToast(state, successMessage, onSuccess?)`, a `useEffect` that toasts and runs `onSuccess` once a bound `useActionState` result's `.success` turns true. Used at 6 call sites across 5 files: `features/users/components/create-user-dialog.tsx`, `features/roles/components/create-role-dialog.tsx`, `features/notifications/components/send-notification-dialog.tsx`, `features/roles/components/edit-role-dialog.tsx`, `features/users/components/edit-user-dialog.tsx` (2 call sites — the update-user form and the password-reset form) — replacing a `useEffect` + `notifySuccess(...)` pattern previously duplicated in every form dialog.
- **Styling**: Tailwind CSS v4, CSS-first configuration — `src/app/globals.css` uses `@import "tailwindcss"` plus an inline `@theme inline { ... }` block. No `tailwind.config.ts`/`.js` file. `postcss.config.mjs` wires in `@tailwindcss/postcss`. Unchanged since the last sync.

## Backend Integration

Real, but partial. `lib/server/http.ts` calls `API_BASE_URL` (required server-only env var, see `.env.example`, resolved per-client via `lib/server/api-clients.ts`'s `ApiClients` registry — only `Backend` exists today), prefixing every path with `api/v1/`. Authorization is now attached via a request-handler pipeline rather than a passed-in token: `lib/server/backend-api.ts` (the entry point for nearly every `features/*/api/*.ts` call) auto-runs `lib/server/http-handlers/bearer-token-handler.ts`'s `bearerTokenHandler`, which reads the ambient session (`getSession()`) and sets `Authorization: Bearer <accessToken>` if present; the 3 pre-session-cookie call sites (`login.ts`, `refresh-token.ts`, `get-current-user.ts`) instead pass the same file's `explicitBearerTokenHandler(accessToken)` directly to `http.ts`. Non-2xx responses now surface a real message where available: `send()`'s new `extractErrorMessage` helper reads the response body and prefers, in order, the app's own `ApiResponse.message`, an ASP.NET `ValidationProblemDetails.errors` map, or a `ProblemDetails.title`, falling back to the old generic "request failed with status N" message only if none parse — this is shared-kernel and applies to every `features/*/api/*.ts` call, not just `users`.

Endpoints currently wired, by feature:
- **`auth`**: `token/token/get` (login, POST — path has a doubled `token/token` segment because `TokenController`'s own route plus its action route both contribute `token`, per an explicit comment in `login.ts`), `token/token/refresh` (`refreshToken()`, POST) — **now wired up**: called from `lib/server/refresh-session.ts`'s `refreshSession()`, itself invoked proactively by `src/proxy.ts` when the access token is close to expiring (see Auth Flow).
- **`user-profile`**: `user_profile` (`getCurrentUser`, GET), `user_profile/token/list` (`listSessions`, GET) and `user_profile/token/revoke` (`revokeSession`, PUT) — both exist and are exported from the feature barrel but have **no UI consumer** yet.
- **`users`**: `user/search` (GET, `searchUsers`), `user` (GET all, `getAllUsers`; PUT-by-id, `updateUser`; DELETE-by-id, `deleteUser`), plus get-by-id, get-by-username, create, force-password — the full `Identity.Api` `UserController` surface, one function per file. Every write path has a real UI consumer at `/identity/users` (search, create, edit, delete, force-password-reset); `get-user-by-id` has a second caller via `get-user-detail-action.ts`, the edit dialog's on-open detail fetch (see [architecture.md](./architecture.md)'s "fetch full detail on open" pattern). `user/search` gained a new consumer this sync, `search-users-action.ts` — used by `features/notifications/components/user-select.tsx`'s on-demand recipient/sender search, not `users-page.tsx`'s own list search. `getAllUsers` is now fully unconsumed again — the Notifications page used to call it unpaginated to populate its recipient picker; that preload is gone this sync (see below). `getUserByUsername` remains unconsumed.
- **`roles`**: `role` (GET all, `getAllRoles`; POST, `createRole`; PUT, `updateRole`; DELETE-by-id, `deleteRole`), plus get-by-id — the full `Identity.Api` `RoleController` surface. Full CRUD at `/identity/roles`; `get-role-by-id` is used via `get-role-detail-action.ts` for the edit dialog's on-open fetch. `getAllRoles` gained a second consumer this sync via the new `get-all-roles-action.ts` — `roles-page.tsx` still calls it directly for the list itself, but `edit-user-dialog.tsx` now also calls it (through the new action) to self-fetch the role picklist on open, since `users-page.tsx` no longer preloads and passes one down.
- **`permissions`**: `permissions` (GET, `getPermissions`) — the full catalog of definable permissions (`PermissionDefinition { name, displayName, parent }`), backing the Roles edit dialog's permissions checklist. **Changed this sync**: no longer fetched server-side in `roles-page.tsx` — `edit-role-dialog.tsx` now self-fetches it on open via the new `get-permissions-action.ts`, alongside its existing role-detail fetch.
- **`dashboard`**: none — `DashboardPage` still reads `STAT_SUMMARIES`/`SAMPLE_USERS` from `features/dashboard/api/sample-data.ts`, which is hardcoded and explicitly commented as not calling the backend yet.
- **`notifications`**: `notification` (GET, `getNotifications` — admin search/list; POST, `sendNotification` — admin send), both permission-gated backend-side (backend also exposes `notification/force_logout`, with **no frontend caller**); `user_notification` (GET, `getMyNotifications` — self-scoped), `user_notification/{id}` (GET, `markNotificationRead` — marks-as-read as a side effect), `user_notification/count_unread` (GET, `getUnreadCount`). Plus a direct WebSocket connection straight to the backend's `/signalr-hub` (`NEXT_PUBLIC_SIGNALR_HUB_URL`, an absolute URL — **changed this sync**: no longer proxied same-origin through `next.config.ts`, whose `rewrites()` was deleted entirely; requires backend CORS for the admin origin), authenticated via a short-lived access token handed to the browser by `getSignalRTokenAction()` — the one deliberate place the access token leaves the httpOnly cookie boundary described in Auth Flow below. **Changed this sync**: `getSignalRTokenAction()` now also proactively refreshes a near-expiry session first (`refreshSessionIfNearExpiry()`), so a long-open tab can't hand SignalR a stale token. The connection itself now retries after a failed handshake (30s, via `use-notifications.ts`'s retryable `connectSignalR`), logging a sanitized error rather than the SignalR client's raw HTML-embedding error message. **Changed this sync**: `notifications-page.tsx` no longer calls `getAllUsers` to populate the recipient filter/picker or resolve the "To" column's display name — the recipient picker (`user-select.tsx`) now searches `user/search` on demand instead, and the "To" column renders `notification.toUserId` directly.

Each API function returns a normalized `Result`/`ApiResponse`-shaped envelope via `guardCall`/`guardResponseCall`/`guardRawCall` in `lib/server/call-guard.ts`, matching the backend's own `Result<T>` envelope (`types/api.ts`).

Both `/identity/users` and `/identity/roles` gate on permissions via `lib/server/authorization.ts`'s `hasPermission(session, userName, permission)`. Permission-string constants now live per-feature rather than in one shared file: `features/users/constants/permissions.ts` (`USERS_PERMISSIONS`) and `features/roles/constants/permissions.ts` (`ROLES_PERMISSIONS`) — the former `constants/permissions.ts` is gone. The string values were also corrected this sync to match the backend's actual format (`Identity.Contracts/Authorization/IdentityPermissions.cs`): lowercase, dotted, `identity`-prefixed (e.g. `identity.users.view`, `identity.roles.manage`), not the previous `Users.View`-style strings, which never matched anything the backend issues. Missing the `*.View` permission renders an inline "Access denied" `Empty` block instead of redirecting; missing `*.Create`/`*.Update`/`*.Delete`/`*.Manage` just hides the corresponding action.

## Auth Flow

Cookie-based session, encrypted at rest, with proactive token refresh:

1. `/login` → `LoginForm` (`features/auth/components/login-form.tsx`) submits to `loginAction`, a `"use server"` Server Action (`features/auth/api/login-action.ts`). When the page was reached via `/login?redirect=<path>`, `LoginPage`/`LoginForm` carry that path through as a hidden `redirect` form field (see step 4).
2. `loginAction` calls `login()` (POST `token/token/get`). On success it also calls `getCurrentUser()` for display/profile data (a failure here doesn't block login — `profile` defaults to `null`). **Permissions and roles are decoded directly from the access token's JWT** (`lib/server/jwt.ts`'s `extractPermissions`/`extractRoles`, reading the `permission`/`role` claim types) — never from the profile API. `SessionData.claims` is the union of every claim in the JWT (`extractAllClaims`) and the profile API's raw claims, deduped via `dedupeClaims()` (`lib/server/build-session-claims.ts`'s `buildSessionClaims()`).
3. The resulting `SessionData` (access/refresh token, absolute access-token expiry, a hard 7-day absolute `sessionExpiresAt` — `SESSION_TTL_MS`, not extended by refresh — claims, permissions, roles, profile) is JSON-serialized and **encrypted** (`lib/server/token-cipher.ts`'s `encrypt()`, AES-256-GCM, keyed by `TOKEN_ENCRYPTION_KEY`) before being written to the `admin_session` cookie (`httpOnly`, `sameSite: "lax"`, `path: "/"`, `maxAge` derived from `sessionExpiresAt`). The former "plaintext for now" state is gone: `TOKEN_ENCRYPTION_KEY` is a hard requirement now (`lib/server/config.ts`'s `getTokenEncryptionKey()` throws if unset) and is read on every encrypt/decrypt via `token-cipher.ts`.
4. On success, `loginAction` reads the submitted `redirect` field and redirects there if it's a safe same-site relative path (`startsWith("/")` and not `startsWith("//")` — guards against an open redirect), falling back to `/`.
5. `src/proxy.ts` (the Next.js 16 "proxy" convention file, successor to `middleware.ts`) runs on every non-static/non-API request. It decrypts and validates the cookie (`lib/server/parse-session.ts`'s `parseSessionCookie()` → `token-cipher.ts`'s `decrypt()`); a missing/expired/malformed session (past `sessionExpiresAt`) redirects to `/login?redirect=<path>` and clears the cookie, and visiting `/login` with a still-valid session redirects to `/`. It calls the shared `refreshSessionIfNearExpiry(session)` (`lib/server/refresh-session.ts` — **changed this sync**: extracted out of `proxy.ts`'s own inline `REFRESH_LEAD_MS` check into a reusable helper, also now used by `getSignalRTokenAction()`, see Backend Integration), which proactively rotates the token via `refreshSession()` (calling the backend's `token/token/refresh` via `features/auth/api/refresh-token.ts` and re-decoding permissions/roles from the newly-issued token) once within `REFRESH_LEAD_MS` (5 minutes) of expiry — a not-due check and a failed refresh both return `null` and neither is treated as a dead session (the code's own comment: multi-tab refresh races can look identical to a real failure, and the backend's own calls still enforce revocation). On a hard navigation (full page load, detected via the `Sec-Fetch-Dest: document` header — Next.js's own client-side route transitions don't send it) or right after a refresh, it also refetches display/claims data via `getCurrentUser()` and rewrites the re-encrypted cookie on both the outgoing request and the response. **This is the token-refresh flow the previous doc version reported as unwired — it is now fully implemented, inside `proxy.ts` rather than a separate scheduled job or client-side call.**
6. `logoutAction` (`features/auth/api/logout-action.ts`, `"use server"`) deletes the session cookie and redirects to `/login?redirect=<path>` (same open-redirect guard as login) or plain `/login`. `components/layout/user-menu.tsx`'s "Log out" item calls it with the current path (`usePathname()` + `useSearchParams()`). **This closes a previously-documented gap** ("Sign-out has no implementation") — session-expiry (via `proxy.ts`) and explicit logout now both funnel through the same `/login?redirect=<path>` → post-login-redirect pattern.
7. `lib/server/session.ts`'s `getSession()` reads and decrypts the cookie (no fetch). `features/user-profile/api/resolve-session.ts`'s `resolveSession()` is now a thin passthrough to `getSession()` — it no longer makes a live `getCurrentUser()` call itself, since `proxy.ts` already keeps the cookie's profile/claims fresh on every hard navigation and after each refresh. Used by the dashboard-group layout, the profile page, and both `UsersPage`/`RolesPage`.

Note: `token-cipher.ts` uses Node's built-in `crypto` module (`createCipheriv`/`createDecipheriv`) directly, and `proxy.ts` has no explicit `export const runtime` pin — see [architecture.md](./architecture.md#known-architectural-risks--debt) for the resulting flag around which runtime this is verified to require.
