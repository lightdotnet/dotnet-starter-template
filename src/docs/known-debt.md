## Architecture decisions pending

- **D1 — `Identity` and `Notifications` CQRS handlers are thin pass-throughs to their service classes.** All `Identity` writes and user search dispatch through mediator commands/queries (`Identity.Api/Application/Users/{Commands,Queries}`, `Identity.Api/Application/Roles/Commands`), and every `Notifications` controller action now does the same (`Notifications.Api/Application/Notifications/{Commands,Queries}`, added 2026-09-05). In both modules controllers only bind the module's `Contracts` DTO/route param and dispatch a command/query, but every handler just forwards to the service layer — `IUserService`/`IRoleService` in `Identity`, `INotificationService`/`IHubService` in `Notifications` — which still holds the logic; the one exception is `Identity`'s `SearchUserQueryHandler`, which queries `UserManager<User>` directly. Decide: inline the service logic into the handlers and demote the services to internal read-only helpers (the `SearchUserQueryHandler` model), or keep the services as the logic layer and treat the handlers as a deliberate uniform entrypoint (worth it for the shared `LoggingBehaviour`/`ValidationBehaviour` pipeline). *(User: to be implemented separately.)*
- **D2 — Soft-delete is wired up but disabled.** `IdentityDbContext` calls `AuditEntries(..., enableSoftDelete: false)` even though `User` implements `ISoftDelete` and `AuthenticationService.CheckInvalidUser` checks `user.Deleted != null` (currently dead code — `AuthenticationService` short-circuits on `user is null` first, so this is an audit-trail/anonymization gap, not a login-bypass risk). `UserService.DeleteAsync` (`Services/UserService.cs`) hard-deletes immediately after `User.Delete()` anonymizes the row, wasting that work; a hard-deleted user's `Id` also orphans any FK/audit field that referenced it (e.g. `UserSessions.UserId`). Decide: flip `enableSoftDelete: true` in `IdentityDbContext.SaveChanges[Async]` (one-line change — `TrackingExtensions.AuditEntries` already does the stamping), or remove `ISoftDelete`/`Deleted`/`DeletedBy` if hard delete is genuinely intended.
- **D4 — `GET user` vs. `GET user/search` coexist.** `UserController` exposes both an unbounded `GET user` (`IEnumerable<UserDto>`) and a paginated `GET user/search` (`PagedResult<UserDto>`, query params via `Identity.Contracts/SearchUserRequest.cs`) for the same read use case. Decide whether `GET user` is an intentional "admin/all" escape hatch or should be deprecated now that paginated search exists — currently organic drift, not a documented decision, and a future module has no precedent to follow.
- **D5 — Cross-module display labels are denormalized snapshots with no backfill.** `Approval` cannot resolve identity/organization data, so the calling side supplies `ApprovalRequest.RequesterName` / `ApprovalStep.ApproverName` at creation time and the module stores them verbatim (same rationale as `Notifications`' caller-supplied `fromName`). `LeaveManagement` has the same exposure a second time: it resolves `RequesterName` server-side via `Organization`'s `IOrgDirectoryService.GetEmployeeNameAsync` rather than trusting the client, but the resulting label is still written once into `ApprovalRequest.RequesterName`/`ApprovalStep.ApproverName` and never re-synced. Either way, these go stale if the underlying user/employee is later renamed, and there is no re-sync path. Accepted as the cost of the "Approval never reaches into other modules" boundary; revisit only if stale approver/requester labels become a real complaint.

## Correctness / performance

- **P4 — `IServiceClaimService` has no registered implementation** (commented out in `Identity.Api/DependencyInjection.cs`; interface in `Identity.Contracts/Services/IServiceClaimService.cs`). Either implement and register it, or remove the unused contract. *(User: later.)*
- **P5 — `IdentityClaimQueryExtensions.CheckUserHasClaimAsync` is dead code** (`Identity.Api/Services/IdentityClaimQueryExtensions.cs`, never called). Wire it into a permission check or remove it. *(User: later.)*
- **P6 — Domain-event dispatch convention bypassed in `Identity`.** `DispatchDomainEventsExtensions.DispatchDomainEvents` (`src/Persistence/Extensions/`) is never called from `IdentityDbContext.SaveChanges[Async]`; `UserCreatedEvent` is instead published manually via the mediator from the `CreateUserCommandHandler`. Related to D1 — once the CQRS handler / service split is settled, make dispatch consistent.
- **P7 — `CreateEmployeeLoginCommandHandler`'s cross-module create is still not fully atomic.** The concurrent-double-submit hole is closed (the link is now claimed with a conditional `ExecuteUpdateAsync` on `UserId IS NULL`, and the freshly minted Identity user is deleted via `IUserService.DeleteAsync` when that loses the race or when `SetClaimAsync` throws). Residual gaps: (1) the conditional `ExecuteUpdateAsync` bypasses the audit interceptor, so linking does not stamp `Employee.LastModified`/`LastModifiedBy`; (2) the compensation (`DeleteAsync` + releasing the link) is itself best-effort — if it throws, an orphan Identity user can still remain. A durable fix needs an outbox/saga or a real distributed transaction.
- **P8 — `LeaveManagement`'s approval-create/cancel compensation is best-effort, same shape as P7.** `CreateLeaveRequestCommandHandler` removes the just-inserted `LeaveRequest` row if `IApprovalService.CreateAsync` fails, and `UpdateLeaveRequestCommandHandler`/`DeleteLeaveRequestCommandHandler` call `IApprovalService.CancelAsync` before mutating/removing the local row — none of this is wrapped in a real cross-module transaction, so a crash between the two calls can leave the `LeaveRequest` row and its `Approval` counterpart out of sync. `LeaveRequestStatusSync.ReconcileAsync` (polling `IApprovalService.GetByRequestAsync` on every read) papers over drift for status specifically, but not for an orphaned `Approval` request left behind by a failed local delete.
- **`Notifications`: no index on `Status`.** `NotificationDbContext`'s only index is `HasIndex(x => x.ToUserId)`, but both list queries and `CountUnreadAsync` filter on `Status` (often combined with `ToUserId`). Performance follow-up candidate at scale, not proven today.
- **`ApprovalService.GetByRequestAsync` returns the most recent of N matches, silently.** `(RequestType, RequestId)` is a non-unique opaque reference (a caller can re-raise a request for the same source record after a rejection), so the query orders by `Created` desc and takes the first rather than throwing on more than one. A caller that assumes a strict 1:1 mapping between its record and an approval request will not be told when that assumption breaks. `LeaveManagement` currently never re-raises a request for the same `LeaveRequest.Id` (a resubmission cancels the old one first), so it isn't yet exposed to this ambiguity in practice.
- **`NotificationConstants.SERVER_NOTIFICATION` is unused.** Defined but the actual `SendAsync<T>` calls use `typeof(T).Name` for the SignalR event name instead — don't assume the constant is the real event name.
- **`HubService.NotifyAsync` (broadcast) has zero callers** — dead capability.
- **Migration-time domain-event dispatch may silently miss module handlers.** `MigrationsExtensions.AddMigrationsServices` (`src/Persistence/MigrationSupport/`) registers mediator handlers via `Assembly.GetExecutingAssembly()`, which resolves to the `Persistence` assembly, not `Identity.Api`/`Notifications.Api`/`Organization.Api`/`Approval.Api`/`LeaveManagement.Api`. Revisit once a module actually relies on migration-time dispatch.

## Security / authorization

- **`GET employee/search` is readable by any authenticated user, by design — the PII boundary now lives in one `.Select`.** The class-level `[MustHavePermission(Employees.View)]` gate was removed from `EmployeeController.SearchAsync` so the create-approval-request approver picker (and any future company-directory feature) can look employees up; `GET employee/{id}` and every write stay permission-gated. `SearchEmployeesQueryHandler` therefore projects only basic directory fields (name, code, email, phone, employment status, avatar, company/user id) via an explicit `.Select` — any sensitive column added to `Employee` later (national id, date of birth, address, …) is exposed company-wide the moment it is added to that projection. Keep the search projection slim; serve sensitive fields only from the gated by-id endpoint.
- **`LeaveManagementPermissions` has no `View`/`ViewAll` split — `Requests.Manage` alone grants view-all.** Every other module's admin-facing permission catalog separates "view" from "create/update/delete" (e.g. `Approval.Requests.ViewAll` is read-only by name). `LeaveManagement` instead has a single `leave.requests.manage` permission that grants both view-all and delete-any. Not a vulnerability today (no other capability to separate it from), but a future manage-adjacent capability (e.g. a read-only HR auditor role) has no permission to slot into without adding a new one.

## Structural / code quality

- **`Identity` predates the module structure convention** (adopted 2026-07-30) and doesn't fully conform: internal layering is informal (folder-based, not compiler-enforced) and CQRS handlers still delegate to the traditional service classes (see D1). Treat as pending `Identity` cleanup, not a second convention. `Notifications`/`Organization`/`Approval`/`LeaveManagement` (all built after the convention) do conform.
- **`ApiControllerBase`/`VersionedApiController` duplicate a `_mediator` backing-field + lazy `Mediator` property** (`src/Infrastructure/Endpoints/`). Likely unavoidable since they derive from two different vendor base classes; revisit if the vendor library ever offers a shared base to consolidate into.
- **`UserSession` extends the plain vendor `Entity` base type, not `AuditableEntity`** — no decision made on whether it should carry an audit trail.
- **`Entities/UserToken.cs`** (ASP.NET Core Identity's built-in `IdentityUserToken<string>`, external-login-provider token store, no business logic touches it) sits in the same `Entities/` folder as `UserSession` (this module's actual JWT/session entity) — "token" means two unrelated things in this module. Low-cost mitigation if it comes up again: a one-line comment on `UserToken.cs`, or grouping ASP.NET Identity's built-in entities separately from module-specific ones.

## Test coverage

- **No `tests/Notifications.Tests` project** — `Identity` has `tests/Identity.Tests` (100 tests), `Organization` has `tests/Organization.Tests` (63 tests), `Approval` has `tests/Approval.Tests` (57 tests), `LeaveManagement` has `tests/LeaveManagement.Tests` (30 tests); `Notifications` still has no automated coverage.
- **No provider-specific migration smoke test.** The `CreateApprovalSchema` / `CreateOrganizationSchema` / `CreateLeaveManagementSchema` baselines are exercised only through the Sqlite in-memory test hosts and `dotnet ef migrations script`. A real MSSQL/PostgreSQL run (schemas, filtered unique index on `Employees.UserId`, the `Restrict` FK on `ApprovalRequests.DocumentTypeId`) has not been done in CI.

## Dependency hygiene

- **Likely dead package references** (no source usage found): `Lightsoft.EventBus` (`Shared.csproj`), `Lightsoft.FileGenerator` (`Infrastructure.csproj`). Verify and remove if confirmed unused.
- **Undeclared transitive dependencies** — compile only because a `ProjectReference` happens to bring the package along:
  - `Infrastructure` uses `Mapster` and `Lightsoft.AspNetCore.Authorization`/`Lightsoft.Result` without declaring either (rides on `Shared`).
  - `Identity.Api` uses `Lightsoft.AspNetCore.Authorization`, `Lightsoft.Result`, `Lightsoft.Extensions`, `Lightsoft.Mediator` (via `GlobalUsings.cs`) without declaring any of them.
  - `Identity.Api`'s `SearchUserQueryHandler` uses `Light.Specification` (`WhereIf`), provided by `Lightsoft.EntityFrameworkCore` — declared by `Persistence.csproj`, not `Identity.Api.csproj`, riding in transitively.
  - `StarterKit.WebApi` uses `Lightsoft.Serilog` without declaring it (only `Infrastructure.csproj` does).
  - Fragile: if an upstream project ever drops one of these packages, downstream projects break with no direct signal why. Recommend each project explicitly declare what it directly uses. `Organization`/`Approval`/`LeaveManagement` (both `.Contracts` and `.Api` projects) do not have this problem — see `dependency-graph.md`.
